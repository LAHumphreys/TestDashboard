## 0. The operating pattern (same as the last two nights — re-arm it)

- **Sonnet implements, the coordinator reviews.** One implementer
  subagent per package, launched in the background; continue the SAME
  agent with follow-up messages rather than respawning (it keeps its
  context). Agents return summaries, never file dumps.
- **Review gate before every push:** read the diff at the critical
  surfaces yourself, run `python -m unittest discover` yourself, THEN
  push; check all four CI legs (`gh run list --branch <b>`); a red leg
  is fixed before anything else proceeds.
- **Resumability:** keep a TaskList entry per phase with instructions
  in the description; arm an HOURLY fallback wakeup (ScheduleWakeup,
  3600s) whose prompt says: check the task list, if an agent/background
  command runs then just re-arm, otherwise resume from the task
  descriptions; re-arm every turn; stop the loop only when Phase 6 is
  done and the morning summary is written. Completed work = pushed
  commits, so nothing is ever lost beyond one agent round.
- **Server rule:** the manual-test server runs on port 8791 from a
  scratchpad COPY of the dev database — never the repo-root
  `testboard.db`. Python changes require a server restart; static
  files do not. A fresh perf log on each restart.
- **Guardrails, verbatim:** never touch `master`, `wp-18-timeline`,
  `wp-14-in-run-progress`, or the repo-root `testboard.db`. Commit
  trailers per CLAUDE.md session instructions. Measurements are
  dev-labelled. Guard tests are widened, never weakened.

## 2. Phase 3 — the sanity net

**Why it exists:** every gotcha of the last 48h was one of SIX classes,
each found by a human click. The net automates exactly those classes so
the morning does not re-find them. Build it as a repeatable harness —
API assertions via a python script in the scratchpad, frontend walks
via the `.scratch/` node DOM-shim harness (extend it; it is gitignored
tooling) — and run the WHOLE net after Phase 1, after Phase 2, and
after any Phase 3/4 fix. It must run in minutes, unattended.

The six classes, each with its checks:

1. **Scope-dropping links.** For EVERY link/button the pages render
   under a build-scoped, product-scoped, and mixed configuration:
   follow the href, assert the landing page's scope params match the
   origin's (product adoption, stream carriage, environment
   preservation). WP-24's builder makes this near-tautological — the
   walk proves the builder is actually used everywhere.
2. **Param collisions & stale scope.** Drive every scope control
   (product switcher, Build picker, Compare-to, test-page switcher)
   through every transition incl. back-to-mainline and cross-product;
   assert the URL after each change has no stale narrower params and
   explicit-choice-vs-absence is never ambiguous.
3. **Unscoped catalogs.** For each product: every dropdown/list on
   every page contains ONLY that product's values (environments,
   scripts, streams). Assert against the API AND the rendered DOM.
4. **Dishonest empties.** For every page, force the empty case (a
   scope with no data) and assert the empty state SAYS something
   specific (names where data is, or why there is none) — never a bare
   blank. Timeline/Time per ONE_KIND §2b, watch error cards, delta
   "no tests in this delta", Corvus's zero-stream UI.
5. **Unexercised UI.** Assert the SEED exercises every category and
   state the UI can render: all five compare categories non-empty
   somewhere, both watch highlight kinds, staleness suffix, origin
   tags, two-tab both tabs, new-tests-with-a-FAIL, no-result both
   directions, an RC pair, a cadenced stream, Corvus. The seed scripts
   (scratchpad `seed_wp23_v3.py` + addenda, updated to `build:`-only)
   are part of the net — if a category is empty, the net fails.
6. **Contract honesty.** Old-client (nine-field) import lands mainline
   and changes nothing visible; `branch:` is rejected loudly
   per-record; `streams_seen` acknowledged for `build:`; byte-identical
   re-push writes nothing (counts assert it).

Plus the standing checks: full suite, dual-backend if the local
MariaDB starts, endpoint timing storm (summary warm/cold, watch,
compare, dashboard — medians recorded, dev-labelled), and the
`actions.js` NUL byte still present.

**Keep the runner scripts** in the scratchpad/`.scratch` with a listing
of them in the morning summary, so the morning's "fix then re-verify"
loop is one command, not archaeology.

## 3. Phase 4 — the three canonical users, from cold

Walk each persona's PRIMARY journey as someone who has never seen the
app, using only what is on screen (no URL hand-editing, no insider
knowledge). At each step ask: is the next click obvious? Does the page
say where I am? Would I know what this number means?

- **The manager (morning glance):** open Watch bare → compose a view
  (two products + an RC + a cadenced stream) using only the composer →
  save default → verify highlights draw the eye to the right cards →
  drill from the worst card to the failing test → back. Friction
  candidates: is the composer discoverable? Do the highlight accents
  read without the legend? Is "slowest environment" wording clear?
- **The delver (mainline triage):** dashboard → worst queue → review a
  failure inline → read output → assign → comment → open the test page
  → history/analytics → timeline of that night → back. This flow
  predates streams and must feel UNCHANGED — any streams-era leakage
  into the plain mainline flow (a label, a control, an extra step) is
  a finding.
- **The RC owner (verify a build):** upload is done (seeded) → find
  the build (picker) → one-glance verdict → walk new failures → check
  a failure's history across builds (dropdown) → assign the RC-blocking
  one → confirm it shows in Open Actions with origin → next morning's
  re-check story. Friction candidates: does the delta view say what
  the columns mean? Is "agree N" comprehensible? Is the verdict line
  visible without scrolling?

Fix what is clearly friction (each fix its own commit, sanity net
re-run). Anything that is a JUDGMENT call goes on the morning decision
list, not into code. Also apply ONE_KIND §2b item 2 (the What's New
rewrite) here if Phase 1 has not already — then re-read it as each
persona: does each bullet tell THEM what they got?
