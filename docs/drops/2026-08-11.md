## Production deployment (MariaDB) — added 2026-08-10, WP-27

**Read this section first if you are deploying to PRODUCTION.** Everything
above this point (and the rest of this note) was written while the staging
box was still SQLite and describes the SQLite migration path — three
`storage.py` migrations that run automatically on the next server restart.
**Production has been MariaDB since 2026-08-07/08's cutover, is currently at
schema v7, and the app never runs DDL on MariaDB** (`testboard/mariadb.py`
refuses a `schema_version` mismatch in either direction) — so a restart with
tonight's code, on its own, does not get production to v10. It needs
`tools/upgrade_mariadb_schema.py` run first, by hand, per
`docs/MARIADB_MIGRATION.md` §G (added the same night as this tool).

**The version gap, stated plainly because it is the single biggest thing
this note cannot promise you:** every check below — the suite, the schema
diff, the `runs` timing — ran against this development box's local MariaDB,
which is **12.3.2-MariaDB**. Production runs **10.3.39**. That is **four
major versions** apart. Nothing in this section is production-verified;
it is 12.3.2-verified, on a machine nothing like production's data volume.
**The only 10.3 evidence that exists anywhere is CI's `python36-mariadb`
job** (a real `mariadb:10.3` service, chosen deliberately to match the
production stream) — check that it is green on this tool's branch before
touching production with it, and treat a red or unrun leg there as this
tool being genuinely unverified, not merely cautious paperwork.

**Suite for this tool, measured on this session's own local MariaDB (DEV
box, MariaDB 12.3.2 — NOT the 10.3 production stream; see the "what was not
verified" note below):** SQLite-only discover **2157 OK** (skipped 1, +1 over
the note's earlier SQLite figure — the one new test needs no server and
pins that this tool's `TARGET_VERSION` still matches
`storage.MIGRATIONS[-1][0]`). Dual-backend discover, `TESTBOARD_TEST_DB_CNF`
pointed at a private sacrificial database (never the shared one) **2933 OK**
(skipped 50), +8 over this session's dual-backend baseline of 2925 — the
8 new tests are `tests/test_upgrade_mariadb_schema.py`'s own: a full v7→v10
run verified clean against the exporter's own v10 DDL, a `--dry-run` that
changes nothing, standalone `verify`, a functional smoke test through real
`Storage` code post-upgrade, and three refusal cases (a v6-shaped database,
an already-v10 database, and a simulated half-upgraded state). Two

checkout artifacts (`core.autocrlf=true` on this Windows box; reproduces on
a completely clean checkout with none of tonight's changes) — not caused by
this work, not fixed by it, out of scope for a backend/schema package.

### The order, top to bottom

1. **Stop the feeder** (same reason as any freeze window — §E.2 of the
   runbook — comments/assignments made during the window are the one
   irreversible loss either way).
2. **Root recreates `testboard_migrate`** (runbook §A.4's `CREATE USER` +
   `GRANT` block, a fresh password never reused from an old note) and the
   operator writes `~/.testboard-migrate.cnf` (§A.9 — mind the inline-`#`
   warning added there tonight: a trailing comment on a value line becomes
   part of the value, it is not stripped).
3. **`mysqldump` production, now, before anything else runs** (runbook
   §G.2): `--single-transaction --routines --triggers testboard > testboard-
   preupgrade-<timestamp>.sql`. This dump — not a transaction, not this
   tool — is the entire rollback plan; MariaDB DDL autocommits per
   statement (say that to whoever is on the call).
4. **`tools/upgrade_mariadb_schema.py upgrade --config ... --dry-run`
   first.** Read the printed plan and row counts. Then the same command
   without `--dry-run`. It refuses to run at all unless `schema_version` is
   7, 8 or 9, and separately refuses (naming the mysqldump) if the actual
   schema disagrees with what the recorded version implies — the shape an
   interrupted run would leave, since the version bump is the LAST
   statement of each step. It runs its own schema verification
   automatically at the end (a diff against a fresh v10 schema built from
   the SAME exporter DDL `tools/migrate_to_mariadb.py` uses, as temporary
   tables inside the same database — the migrate credential has no
   `CREATE DATABASE` privilege, by design, runbook §A.4).
5. **Deploy tonight's code** (the usual stop/copy/pull/start — this drop's
   own instructions apply unchanged for the file copy; only the database
   step above is new).
6. **Restart the server**, not optional (`CLAUDE.md`'s standing rule — a
   stale process serves new HTML/JS against old handlers either way, and
   here it would ALSO still be running the pre-upgrade schema check).
7. **First-hour checks**: open the dashboard, load a test detail page, read
   a run's output, post a comment, make an assignment, open the Build
   picker on any environment that has ever reported a non-mainline result.
   Watch the log for anything from `testboard/mariadb.py`'s schema check —
   its absence is the good outcome.
8. **Restart the feeder** — only after step 6, same reasoning as the
   SQLite runbook's §E.5 (a feeder restarted earlier pushes the freeze
   window's backlog nowhere useful).
9. **Delete `~/.testboard-migrate.cnf` and the `testboard_migrate` account**
   once the above is confirmed quiet. That credential can drop every table
   in the database; it does not live between uses.

### Rollback

**Before step 6:** nothing human has been written yet — restore `testboard`
from the step-3 dump if steps 4–5 went wrong, and leave the old (v7-serving)
code running. **After step 6:** the same rule as every cutover in this
project — rollback is clean only until the first human write, because
comments/assignments/retirements made after the restart exist only in the
upgraded database. Restoring the dump after that point loses them.

### What was NOT verified

- **THE version gap (repeated here because this list is where people
  actually look): this tool has never touched anything but a local
  12.3.2-MariaDB instance on this box. Production runs 10.3.39 — four
  major versions older.** The multi-clause
  `ALTER TABLE ... ADD COLUMN ... FIRST, DROP PRIMARY KEY, ADD PRIMARY KEY
  (...)` statements this tool relies on for the small tables, and the
  plain last-column `ADD COLUMN` it relies on for `runs`, are exactly the
  kind of DDL whose supported algorithms can differ between server
  versions. **Do not treat this as verified until the `python36-mariadb`
  CI leg is green on this tool's branch** — that leg runs against
  `mariadb:10.3`, the same stream as production, and is the only 10.3
  evidence that exists anywhere for this tool.
- **The `runs` ADD COLUMN specifically — the one exposure that scales with
  production's ~4.4M rows.** Locally, on 12.3.2: the plain
  `ALTER TABLE runs ADD COLUMN stream_id BIGINT NOT NULL DEFAULT 1`
  completed in under a second against 500,000 synthetic rows (0.3s total
  for ALL three migration steps combined, `runs` itself timed at
  effectively 0.0s by the tool's own per-statement clock), and forcing
  `ALGORITHM=INSTANT` explicitly on an equivalent statement SUCCEEDED
  rather than being refused — real evidence the instant path applies, not
  an inference from a fast clock. **This is still 12.3.2, still 500k rows,
  not 10.3.39's ~4.4M.** If instant does not apply on 10.3 for some
  reason this box cannot surface, MariaDB falls back to the next InnoDB
  algorithm that fits — normally an online, `LOCK=NONE` rebuild (the
  dashboard stays readable and writable during it, unlike the old blocking
  `COPY` algorithm) — and a rebuild of a table this size should be assumed
  to cost on the same order as this runbook's own measured full-load
  benchmark (§0/§E.1: "tens of minutes at best" for a ~950 MB database).
  The tool now prints `runs`'s row count before touching anything and
  warns loudly, live, if that one statement takes more than 5 seconds —
  if you see that warning, the statement has ALREADY committed
  successfully (DDL autocommits); there is nothing to interrupt, only a
  longer wait than expected.
- **`utf8mb4_nopad_bin` / collation behaviour on whatever exact server
  build is running in production** — this tool trusts the collation
  production was already loaded under (WP-19's cutover); it does not
  re-probe it.
- **Beyond the `runs` ADD COLUMN, every other timing above is still this
  session's local database at a fraction of production's scale (the
  seeded fixture is four rows; the 500,000-row figure above is a separate,
  synthetic probe, still nowhere near 4.4M).** Measuring the REAL window
  needs a copy of production, the same as the runbook's own §E.1 insists
  on for a full migration — this tool has no equivalent
  dry-run-against-a-copy step of its own yet, because there is no easy way
  to copy a live MariaDB database into a scratch one without either
  `mysqldump`-and-reload (which IS step 3's dump, reloaded) or a second
  slice of downtime. If there is time before the deployment window,
  loading the step-3 dump into a scratch database and running the tool
  against THAT first is the closest available equivalent to §E.1, and is
  recommended, not merely optional.
- **Whether any other tenant of this MariaDB instance** (mentioned in
  passing in the cutover's own history — this database is not necessarily
  alone on the server) **is affected by the `ALTER TABLE` locks** the
  upgrade takes. Each `ALTER TABLE` locks only `testboard`'s own tables,
  but a busy neighbour on the same instance could still see contention.

### WP-21 — branches and builds beside mainline (migration 9)

The feature `docs/STREAMS_PLAN.md` §3 describes in full; the shape of it:

1. **A "stream" is `(product, kind, name)`** — `kind` is `branch` or
   `build` (mainline is the implicit, un-droppable stream id 1, seeded by
   the migration itself). A record's stream is resolved ONCE, from the
   import batch's `branch`/`build` field, and its product is fixed at that
   moment from the environment's declared product (WP-20) — renaming an
   environment's product afterwards does not retroactively move a stream.
2. **Import contract** (`POST /api/import`): each record MAY carry
   `branch` OR `build` (never both — `400` if a batch does). The response
   gains `streams_seen`: the sorted list of every non-mainline stream that
   batch touched, as `"branch:<name>"`/`"build:<name>"` strings, `[]` for a
   mainline-only batch. **A response with the key ABSENT (not `[]`) is how
   a new feeder detects an old server** — see the feeder section below.
3. **The legacy-UNIQUE collision case.** `runs`' `(environment, script,
   test_name, start_time)` UNIQUE constraint is frozen since migration 1
   and cannot hold two different streams' runs at the exact same instant
   for the exact same test. This is rare (it needs a branch and mainline
   to report the identical test at the identical microsecond) but
   possible, and the record that loses is **rejected, not overwritten** —
   it comes back in the import response as a rejection with an explicit
   message, never silently dropped and never silently filed into the
   wrong stream.
4. **Mainline is provably unaffected.** `activity_hours`/`script_hours`
   (the Timeline's data) only ever accumulate mainline's own runs;
   un-retirement (a retired test's retirement clearing when it reports
   again) only fires for mainline runs — a branch predating a retirement
   must not silently un-retire it; every estate-wide read (the home
   screen, Open actions, the Timeline, `/api/environments`, `/api/scripts`)
   is hardcoded to mainline with no override parameter at all, so there is
   no query string that could accidentally leak a branch's numbers into
   an estate-wide view.
5. **The Build picker** (`static/streams.js`, dashboard toolbar only) —
   hidden unless the current product has at least one branch/build stream.
   Picking one navigates to `?stream=<id>` and swaps the WHOLE dashboard
   body for the **delta view**: five tiles (new failures, new passes, both
   failing, new tests, no result), an "N tests agree and are not listed"
   line, a coverage line ("N of M tests have a result on this branch"),
   both sides' freshness, a stale-baseline warning when mainline itself
   hasn't run recently, and tabbed paginated tables (mainline's result
   ghosted/outlined, the branch's solid). **A mainline page
   (`index.html` with no `?stream=`) never fetches or renders any of
   this — zero visible change**, pinned by a dedicated test.
6. **Test detail** (`?stream=<id>`) scopes the history table and analytics
   to that stream's own runs, and shows a compare strip (mainline's result
   beside the branch's) for the same test. Comments are never filtered by
   the current stream — the whole thread shows, each comment tagged with
   which stream it was posted from (a batch resolve, not one query per
   comment).
7. **The Watchlist gains an `s:` card** — a branch/build verdict card
   (same compare-vs-mainline headline, both sides' freshness), resolved
   through the same batched storage reads `/api/compare` uses so
   `/api/watch` keeps its one-query-per-derived-table property regardless
   of how many stream cards a URL carries.
8. **New endpoints:** `GET /api/streams?product=` (the picker's data),
   `GET /api/compare?stream=&category=` (the five/six counts plus one
   paginated category; `baseline` must be mainline in this drop — cross-
   branch baselines are WP-22).
9. **`tools/drop_stream.py`** — the `drop_environment.py` analogue for a
   typo'd or dead branch/build stream. Refuses mainline unconditionally,
   `--dry-run` first, confirmation prompt unless `--yes`.
10. **Feeder:** new `--branch NAME` / `--build NAME` flags (mutually
    exclusive). A feeder invoked with either **requires** the
    `streams_seen` acknowledgment in the import response and aborts
    loudly (exit 1, no high-water-mark saved) if it is absent — the only
    way an old server can be told apart from one that silently filed
    everything into mainline. Each stream gets its own state file
    (`feeder_state.branch.<name>.json`), so a branch's catch-up run never
    shares — or fights over — mainline's high-water mark.
11. **Four findings from the first human use of the branch dashboard**,
    added to this same unshipped drop rather than deferred:
    - **The branch band now also shows on the test-detail page**
      (`?stream=<id>`), not only the dashboard — sharing one
      `renderBranchBand()` function, not a second implementation. A
      reader who clicked through from the delta table into a test's own
      page previously lost every indication they were scoped to a
      branch at all; the compare strip alone was not loud enough.
      "Back to mainline" is now the current URL with only `stream`
      stripped, computed the same way on both pages, so the test page's
      link correctly preserves `environment`/`script`/`test_name`
      instead of bouncing to a fixed `index.html`.
    - **Triage from a branch actually works now.** The delta table's
      rows carry the same assignee select and inline Review expander
      (captured output, "View in timeline", a comment box) as every
      other list in the app — item 4 above ("mainline is provably
      unaffected") is unchanged: this reads/writes the (environment,
      script, test_name) triple's ONE assignee, never a stream-scoped
      copy of it. Retirement is refused by construction on a branch row
      (the shared review panel is simply never told a staleness
      cutoff there, so its own gate never opens) — retirement stays a
      mainline-only decision. `/api/compare`'s paginated rows gained
      `stream_run_id`/`stream_start_time` (the branch's own run; null
      exactly when there is nothing on that side to review — no new
      query shape, both already live on `latest_runs`) and `assignee`
      (the triple's current, unpartitioned owner).
    - **Assignment origin is now recordable** — `assignments`/
      `current_assignments` both gained a nullable `stream_id`
      (**folded into THIS drop's migration 9**, not a new migration 10:
      migration 9 was still unshipped when this was found, so no
      database anywhere has the narrower shape it had before the fold —
      see the entry's own comment in `storage.py` for the reasoning).
      `PUT .../assignee` accepts an optional `stream_id`; every existing
      caller that never sends it is completely unaffected.
    - **Open actions shows where an assignment came from.** A row whose
      current assignment carries a non-mainline stream gets a small
      "branch feat/x" tag (batch-resolved per page, the same pattern
      the comments endpoint uses), and — only once at least one
      assignment anywhere carries a stream — a branch-vs-mainline
      filter chip pair next to the existing owner filters. Both are
      genuinely new query surface on `/api/dashboard`
      (`origin=branch`/`origin=mainline`, server-side, same rule the
      existing owner filter already follows) and `/api/summary`
      (`assignment_streams`, the existence signal). Zero visible
      change on any install where no assignment has ever carried a
      stream.

    driven through all four scenarios via the node DOM-shim harness

### WP-22 — release builds + compare-any-two (no migration)

The feature `docs/STREAMS_PLAN.md` §4 describes in full — RCs and release
builds are the same mechanism as branches (`kind='build'`), read
differently: judged against the build before it, re-cut under the same
name, and comparable directly instead of only via mainline.

1. **`GET /api/compare`'s `baseline=` accepts any stream of the SAME
   product**, not only mainline — a build judged against the build before
   it, or one branch against another. Mainline stays the one universal
   exception on either side of the comparison (its `product` is `''` by
   construction, shared by every product). A baseline from a DIFFERENT
   product is refused with a clear 400 naming both — nothing joins across
   products, since they don't share environments.
2. **The Build picker's Builds group**, newest first by `last_seen` —
   version strings are opaque and never parsed (decision §0.7), so recency
   is the only ordering that means anything.
3. **The build-scoped dashboard gains a "Compare to" box**: a plain
   text-with-suggestions field defaulting to the build's own predecessor
   (by `last_seen`) when one exists, else mainline. Picking a different
   build or branch of the same product re-scopes the comparison via
   `?baseline=<id>` — a real navigation, sharable by URL like everything
   else in this feature. A build's page also says when it was built and
   whether anything has run since.
4. **New: `GET /api/tests/{env}/{script}/{test}/streams`** — a triple's
   latest result on every stream that has one, newest first. Powers two
   new pieces on the test page: the **"Every build" disclosure** (this
   test's latest result on every stream of its product, including the
   ones that never ran it, marked plainly as NO RESULT rather than left
   off the table) and a **stream switcher** near the top of the page — the
   specific thing asked for after first human use of WP-21's branch
   dashboard — jumping straight to this test's result on any other stream
   that has one.
5. **The Watchlist's `s:` card works for builds too**: "N tests failing in
   `<name>`", compared against its predecessor build when one exists (the
   same default the dashboard box uses), falling back to mainline
   otherwise. Every place that used to say the literal word "mainline" —
   the delta view's heading, column headers, freshness lines, the branch
   band, this card — now names whatever the ACTUAL baseline is, since it
   is routinely a predecessor build rather than mainline once this ships.
6. **Verified, not merely assumed:** a build rebuild (a second import

### Addendum 4 — summary/watch memoization, one more perf slice (still WP-23, no new migration)

Calibration from the user: the real production estate is 12k tests over
5 environments (largest env ~8k) — the PERF ROUND's dev-scale numbers
above ARE production scale for size, so `/api/summary` at ~205 ms and
`/api/watch` at ~250 ms are day-one experience, not dev noise. This
addendum lands memoization before the drop ships, closing the "reaching
<100 ms needs a second pass" gap the PERF ROUND section above left
open.

**Design: component-level memoization, not full-composition.** Copies
`Storage._trend_cache`'s exact TTL-bounded, write-invalidated pattern —
one shared dict (`_summary_cache`) keyed `(method_name, *scope)`,
`_TREND_CACHE_TTL_SECONDS` (60s) reused rather than duplicated, cleared
unconditionally by every mutator that can change a cached answer. Chosen
over caching `_handle_summary`'s whole composed response because
`_handle_watch` has no equivalent composed call — it calls
`summary_rollup`/`test_counts_by_environment`/
`latest_run_time_by_environment` directly, so only a memo living BELOW
both handlers, in `Storage`, can serve both. Eight methods memoized:
`summary_rollup`, `queue_counts`, `status_queue` (all 6 kinds),
`test_counts_by_environment`, `latest_run_time_by_environment`,
`environments`, `scripts` — widened from the coordinator's original
five (`summary_rollup`/`queue_counts`/`failure_streak_bounds_many`/
`latest_run_time_by_environment`/`test_counts_by_environment`) once
attribution showed the named five alone would land around 76 ms warm,
short of the 30 ms target; `status_queue`'s six row-fetches (34 ms
measured, the single biggest uncached cost after the named five) and
the two cheap catalog reads made up the difference.
`failure_streak_bounds_many` is memoized PER ENTRY, in a SEPARATE dict
(`_streak_cache`, cap 4096 vs the request-composition cache's 128) —
a queue's row set changes page to page even when the underlying
failures do not, so caching the whole batch call would rarely hit;
caching per `(stream_id, environment, script, test_name, start_time)`
means a still-failing test is a hit across pages.
`/api/watch` was changed to compute its estate-wide rollup cutoff via
`_pass_view` (the same function `/api/summary` already used) instead of
`now()` — the existing code already documented "any value works" for
that argument, so switching costs nothing and lets the two endpoints'
`summary_rollup` calls land on the SAME cache key on the common
unscoped load. Verified directly: a warm `/api/watch` call issued right
after a warm `/api/summary` call adds ZERO new cache entries and costs
4.8 ms; the same call against a cold store costs 24.2 ms.

**Bug found and fixed before measuring:** the first version shared ONE
128-entry cache between the ~20 request-composition keys and
`failure_streak_bounds_many`'s per-triple keys. Profiling a "warm"
repeat `/api/summary` call that was still costing 28 raw SQL statements
found why: one unscoped request on the production-shape estate touches
139 distinct keys once every queue kind and every FAIL row's streak
entry is counted — over the 128 cap on its own, so the cap-then-clear
policy fired MID-request and wiped `summary_rollup`/`queue_counts`/the
earlier-processed queue kinds before the SAME request finished using
them. Fixed by giving `failure_streak_bounds_many` its own cache dict
(`_streak_cache`, cap 4096, sized to the estate's plausible
simultaneously-failing-test count rather than to one request). Confirmed
by re-running the same profile: all 6 `status_queue` kinds and
`summary_rollup` now persist across repeat calls.

**Measured, HTTP end-to-end, a COPY of the shared server's actual
production-shape database (5 environments, ~65k runs, ~12.8k mainline
tests — the live estate this session's own calibration refers to, not
a synthetic one), 15 samples after 3 warmup. Before/after run as a
genuine paired A/B**, not two measurements taken minutes apart: a
`git worktree` at this branch's pre-change tip (`0a44ea0`) and the
working tree with this change, both serving the SAME database file,
each on its own scratch port (never the shared 8791 instance),
benchmarked back-to-back in the same session so OS-level file-cache
warmth — which an EARLIER same-session measurement showed can move
these numbers by 2–3× on its own — cannot be mistaken for the memo's
own effect:

| Endpoint | Before (0a44ea0) | After (warm) |
|---|---|---|
| `/api/summary` (full) | median 62.8 ms, p95 101.7 ms | median **4.5 ms**, p95 6.3 ms |
| `/api/summary?parts=headline` | median 39.4 ms, p95 45.4 ms | median **3.2 ms**, p95 4.5 ms |
| `/api/watch`, 8 mixed cards (5×`e:`, 2×`p:`, 1×`s:`) | median 107.8 ms, p95 155.8 ms | median 68.6 ms, p95 94.6 ms |
| `/api/watch`, same 7 `e:`/`p:` cards, no `s:` | median 26.3 ms, p95 34.1 ms | median **11.9 ms**, p95 16.3 ms |

**Cold** (one request against a just-started process, before its memo
has anything in it): three paired samples, before {98.9, 131.3, 115.5}
ms, after {148.8, 185.6, 115.7} ms — same order of magnitude either
way, with after running somewhat higher on 2 of 3 samples, plausibly
the small fixed cost of the cache-key construction and lock/dict
lookup that now runs on every cached call whether it hits or not. Not
resolved further with three single-request samples; the point of a
cold measurement is that the memo cannot yet be helping, and it isn't
here.

Warm `/api/summary` beats the 30 ms target by an order of magnitude
(4.5 ms) once the cache-thrashing bug above was fixed — the SAME
paired-A/B methodology against the pre-fix code measured ~61 ms warm,
a real improvement over the 62.8 ms baseline but barely, and the wrong
number to have shipped.

**`/api/watch`'s remaining 68.6 ms is mostly attributed, and closing it
further is NOT this memo's job:** profiling isolates `compare_counts_many`
(39 ms) plus `known_environments` (4 ms), both driven by the `s:` (stream
comparison) card — a pre-existing, already-flat-per-request cost
`_handle_watch`'s own docstring calls out separately from the memoized
methods, and the coordinator's instruction was explicit: watch reuses
the summary memo where it reads the same shapes, and does NOT get a
second cache layer of its own. Dropping the one `s:` card from the same
8-card mix (last row above) shows the memoized components alone land at
11.9 ms, down from 26.3 ms before — confirming the `s:` card, not the
memo, is most of the remaining 8-card cost, and that the memo IS
helping the parts it was built for.

**A side effect worth naming**: `status_queue`'s `ORDER BY environment`
with a `LIMIT` and no unique tiebreak means two identical executions of
the SAME query could previously return different subsets of a capped
queue (observed directly while debugging the cache-thrashing bug: two
calls with byte-identical arguments returned rows from different
environments). Pre-existing, unrelated to this change, deliberately not
fixed here — but the memo now means a repeat load INSIDE the TTL
returns the exact same rows each time, where before it could silently
shuffle. Worth knowing before someone rediscovers the shuffling's
absence in six months and files it as a bug.

**Invalidator audit** (the trend cache's clear list was the checklist,
per the coordinator's instruction):

| Mutator | Invalidates? | Why |
|---|---|---|
| `upsert_runs` (when it inserted/updated) | yes | every cached method reads `latest_runs` |
| `delete_stream` | yes | same table, plus removes the stream's own partition |
| `prune_runs_before` | yes | same table |
| `delete_environment` | yes | same table |
| `set_assignee` | yes (NEW) | `queue_counts`'/`status_queue`'s assigned/mine predicates read `current_assignments`, which the trend cache never needed |
| `set_retired` | yes (NEW) | `summary_rollup`/`queue_counts`/`status_queue`/`test_counts_by_environment` all read `test_retirements`'s retired flag; it also posts a comment (see below) |
| `add_comment` | yes (NEW) | `status_queue(with_latest_comment=True)` caches the comment TEXT itself, not just a row count |
| `set_environment_product` / `clear_environment_product` | **no, audited** | every cached method takes its product/environment scope as an explicit `environments` allow-list argument rather than joining `environment_products` — a remap changes which KEY a request computes, never makes an existing entry wrong |

**Tests:** `tests/test_storage.py::SummaryCacheTest`, 21 new tests —
repeat-call-is-a-cache-hit (query-count, not value, for each of the 8
memoized shapes), one test per invalidator above, scope-key isolation
(a product/environment allow-list and a branch stream never serve
another scope's entry), TTL expiry, and the audited "no invalidation
needed" case above proven rather than merely asserted. Two existing
guard tests (`TestWatch.test_query_count_does_not_grow_with_card_count`,
`TestWatchStreamCards.test_query_count_does_not_grow_with_s_card_count`)
started failing once the memo made a SECOND identical request cheaper
than the first — widened (never weakened) per house rules: each now
primes an identical untraced warm-up call before tracing, so the
comparison holds cache STATE equal between its two sides and the
original card-count invariant is still enforced, at the new (lower)
warm-cache cost. `SummaryCacheTest`'s 11 query-count tests are excluded
on the MariaDB leg (`tests/test_mariadb_backend.py`, same
`sqlite3.set_trace_callback`-is-SQLite-only reason every other
query-count test there already carries); the memo's correctness itself
is NOT backend-specific and the other 10 value-based tests in the class
run and pass on both backends.

**Dual-backend:** full suite green against local MariaDB 10.3.

**Not verified:** no frontend files changed, so nothing new to render.
The production-shape database used for measurement is a static COPY
(never re-fed during this session) — on a live server being fed every
10 minutes, `summary_rollup`/`queue_counts`/`status_queue`'s cutoff
argument is usually DATA-derived and stable across nearby requests (a
covered pass's start time), giving the same warm-cache behaviour
measured here; on an estate that has gone quiet long enough to fall
back to the 36-hour wall-clock window, that specific cutoff-keyed cache

### WP-28: `--url-prefix` for nginx front-doors, both shapes always accepted

**What changed.** The server now strips a configurable URL prefix (default
`testboard`, matching the nginx path this deploy will eventually sit behind)
at the top of routing, before any path-traversal check runs. Nothing about
today's deployment shape changes: **bare paths (`/api/summary`,
`/index.html`, feeder POSTs) keep working exactly as before, unconditionally**
— the server accepts both the prefixed and bare forms of every path on the
same port, always. This is a prerequisite for putting nginx in front of the
box, not a statement that nginx is configured yet.

- New flag: `run_server.py --url-prefix PREFIX` (default `testboard`; pass
  `--url-prefix ""` to disable prefix handling entirely — fully backward
  compatible with every deployment that has no nginx in front today).
- A request for exactly `/testboard` (no trailing slash) gets a 307 (not
  301/302/308) redirect to `/testboard/` — 307 specifically because it
  preserves the HTTP method like 308 but is never cached as permanent by a
  browser, so it costs nothing to reverse if the prefix ever changes.
- Matching is by path **segment**, not string prefix: `/testboardXtra/...`
  does **not** match and falls through to ordinary (404) handling.
  `/testboard/testboard/api/...` (double-prefixed) is stripped exactly once.
- Frontend: every API call in `static/*.js` now uses a relative URL
  (`api/summary`, not `/api/summary`), which resolves correctly under
  either shape with zero prefix-awareness in the JS itself — this needed no
  new frontend logic, only removing leading slashes at the call sites.
  Guarded permanently: `tests/test_frontend_calls.py::RootAbsoluteApiUrlTest`
  fails the build on any root-absolute `/api/...` literal reappearing
  anywhere in `static/`, including inside the two files that legitimately
  contain a NUL byte (`actions.js`, `test.js`), which a plain grep silently
  treats as binary and skips.

**Sample nginx config — the tested, non-stripping shape.** This is the
shape every test in this drop exercises (by hitting the backend port
directly with prefixed paths, simulating exactly what this config passes
through). Deliberately **no trailing slash** on the `location` and **no
trailing slash** on `proxy_pass`'s upstream URL: with a trailing slash on
`location /testboard/ { ... }`, nginx would never forward a bare
`/testboard` request (no trailing slash) to the backend at all, so the
307-to-trailing-slash redirect above would never fire through the front
door — only when hitting the backend port directly, which is not the real
path. Without the trailing slash, `/testboard`, `/testboard/`, and
everything under it all pass through untouched, and the backend — not
nginx — makes every prefix decision, matching this drop's "strip once, at
the top of routing" design:

```nginx
location /testboard {
    proxy_pass http://127.0.0.1:8000;
}
```

(Port 8000 is this drop's example; use whatever port `run_server.py` is
actually bound to.) Note nginx's own location matching here is a coarser
string-prefix match than the backend's segment-boundary check — it would
also forward `/testboardXtra` through — but that is not a correctness gap:
the backend still rejects it as unmatched and 404s, exactly as it does
today with no nginx involved.

**Decision the operator does not have to make yet.** This flag ships
default-on (`testboard`) but requires no action: **nginx may not be
configured on production at all yet**, and nothing in this drop assumes it
is. Every existing bare-path caller — the browser hitting the box directly,
every currently-deployed feeder — is completely unaffected either way.
Putting nginx in front, using the block above, is a follow-up step whenever
it's ready, not part of this drop's rollback surface.

**Feeders:** unchanged. They talk to the backend port directly
(`--url http://host:8000`), never through nginx or `--url-prefix` — no
feeder config changes for this drop, at rollout or ever, regardless of
whether/when nginx is added in front.

**Verified beyond the source-level guard tests.** A dedicated server-boot
test module (`tests/test_url_prefix.py`, 23 tests) starts a real threaded
server and exercises: both shapes for every path type (GET, POST/mutation,
index, static asset), the segment-boundary non-match, the double-prefix
collapse, a percent-encoded prefix attempt, the 307's exact status code and
query-string preservation, path-traversal rejection under a prefix
(widened, not weakened, from the existing unprefixed guard), a feeder
import round-tripping on the bare path against a prefix-**enabled** server,
and prefix-disabled (`--url-prefix ""`) and custom-prefix configurations.
The DOM-shim sanity net (`.scratch/net/run_net.py`, not part of the repo)
was run twice against the same server binary — once unprefixed, once
`--url-prefix testboard` — both PASS; the prefixed run's own checks assert
every link a rendered page produces, and every fetch call the frontend
code actually issues, resolves back **inside** the prefix it was loaded
under, not just that it renders without error.

**What this pass does NOT prove.** No nginx process ran anywhere in this
verification — every "prefixed" test simulates the pass-through shape by
requesting prefixed paths directly against the backend port, which is
sound for what the backend does but does not exercise nginx's own request
handling, headers, or config syntax; the sample block above is untested as
an nginx config, only as the shape that produces the exact request/response
pairs this drop's tests make. No browser rendered any page either: the
DOM-shim net proves link and fetch-URL *resolution* under a prefix, not
layout, CSS, or anything a real browser's network panel would show.

**Nothing deployed changes.** The feeder currently running in production
is untouched: it keeps running off its checkout (`feeder/` +
`run_feeder.py`), and this drop does not migrate it, reconfigure it, or
require anything of it. It becomes a migration candidate later, once the
new form has proven itself on a new product.

**What is new** is a second, self-contained way to contribute results,
for products onboarding from here on: ONE file a product checks into its
own repository, rather than a link to a full checkout of this repo.
`clients/feeder.py` (Python 3.6) and `clients/feeder.tcl` (vanilla Tcl
8.5) are the same engine in two languages, each with a marked
"IMPLEMENT THIS" slot at the top for the site's own result-reading
function and a do-not-edit line below it. `docs/FEEDER_TEMPLATE.md` is
the brief a site (or its AI assistant) works from.

**The invocation model differs from the deployed feeder, deliberately.**
These are called by the test framework during its own CLEANUP phase,
once per suite execution, with the environment and build passed as
arguments. They do NOT poll, have NO daily mode, and keep NO
high-water-mark state. The only thing they write to disk is a replay
file when a submit fails, drained by the next invocation.

**Exit codes are a contract** the framework owner can rely on:

| Code | Meaning | Should it fail the cleanup? |
|---|---|---|
| 0 | Every valid record accepted | No |
| 1 | Server unreachable or refused; batch saved to a replay file | **Results are SAFE** — the submit is deferred, not lost. Treat as a warning |
| 2 | Usage or validation error; nothing was sent | Yes — the invocation is wrong |

Worst case is bounded: retries and backoff are capped at ~115s by
construction, and a black-holed server port was measured exiting 1 at
**51s** on this box (DEV timing, not production).

**Operator impact: none today.** No new service, no new port, nothing to
install. Sites reach the dashboard's backend port directly over plain
HTTP — never through nginx and never with the `--url-prefix` from WP-28.
That is why WP-28's bare-path acceptance is unconditional.

**What was NOT verified, specifically.** `clients/feeder.tcl` targets Tcl
**8.5**, and no 8.5 interpreter has ever executed it. There is not one on
any developer box or in CI: the box it was written on runs 8.6.18 and
CI's Tcl leg runs 8.6.14. What exists instead is a static gate
(`tests/test_tcl_compat.py`) that rejects 8.6-only constructs
(`try`/`finally`, `throw`, `lmap`, `string cat`, TclOO, coroutines and
others), plus a conformance suite that runs all 8 scenarios against BOTH
engines on every push. So the claim "it runs on a real tclsh" is proven;
the claim "it runs on 8.5" is argued, not demonstrated. If the first
onboarding site is genuinely on 8.5, treat its first run as the
experiment it is.
