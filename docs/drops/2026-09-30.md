## What changed

**Fixed**

- **A comment made from a build's row was recorded with no build** (WP-35).
  Only the test page's own comment box tagged a comment with the build it
  was made from. The Review panel did not, and the note on a bulk assignment
  was written with no origin whatever the row said. Both now do. Comments
  already stored are not rewritten.
- **Refresh on a build's "Difference from" tab drew mainline's dashboard
  underneath it**, once "Its own results" had been opened (WP-33). The
  reverse — Refresh on "Its own results" bringing the comparison back —
  had the same cause.
- **A Review panel open on that tab made the next re-render throw** and the
  list stop at that row (WP-35).
- **A stream's "latest run" was found by walking `runs` backwards** until it
  met one of that stream's (WP-36). Instant for whichever stream ran last;
  16.8 ms on the dev estate for a build that last ran three days earlier,
  and growing with every night since. It is now one index seek.

**Faster** (WP-36) — cold, in-process, master against this drop alternately;
dev-scale SQLite with a 10,326-test build beside mainline's 24,854:

| Request | master | this drop |
|---|---|---|
| Home headline, all products | 76 ms | 36 ms |
| Home headline, one product | 55 ms | 34 ms |
| A build's page: header | 33 ms | 0.1 ms |
| Product list, on Time / Timeline / Watch / test / script pages | 76 ms | under 0.1 ms |
| Timeline (what Follow repeats every ten seconds) | 17 ms | 11 ms |

Why "cold" is the figure that matters: results are pushed during a run, and
every import that changes a row clears every memo. For the hours a run lasts,
nothing is served from one.

**WP-38 — the day's pushes, and the first paint** (added 2026-09-30)

Production pushes results throughout the day now: mainline's through the
morning, builds' into the afternoon. Every push used to drop every memo,
so nobody was served from one. Now a push drops only the `(stream,
environment)` pairs it wrote. Replayed over HTTP on the dev estate — a
push of 200 records, then a home-page load, twenty times:

| | before | after |
|---|---|---|
| afternoon: pushes into a build | 64 ms median | **14 ms**, memo hits 120 / misses 0 |
| morning: pushes into mainline's largest environment | 65 ms median | **32 ms** |
| the push itself, 500 records | 42–54 ms | 42–54 ms (unchanged; alternated, five rounds) |

Also: every page names its whole module graph up front (`modulepreload`),
so the browser fetches it in one go rather than a layer at a time; and the
home page ships its "Latest results" frame with placeholder tiles, on
screen before any script runs. **"Hangs for a few hundred ms before
rendering anything"** was the report; what these two remove is the
dependent round trips before the first request for data. What they do not
remove is a wait for a free worker — see the decision below.

## The decision you have to make

**Leave the counters on, or start with `--no-metrics`?** Recommended: leave
them on. They are in memory, take no lock to record, and measured at 1.3
millionths of a second per storage call; a warm home headline was 0.630 ms
without them and 0.647 with. `--no-metrics` exists so that there is a switch
if that is ever wrong on your hardware. With it, the Metrics page still shows
the database and says the rest is not collected.

**Consider `--workers 16` on production.** The pool is 8 by default and a
worker is bound to a connection. A browser opens up to 6 connections to
load a page; every feeder pushing at the time holds one more. With
mainline and several builds pushing through the day, the pool is contended
by the third person to open a page, and a request queued for a worker is
the one delay nothing in this drop can shorten. On MariaDB a worker costs a
thread and a connection to the daemon and nothing else (SQLite divides its
page cache by the count, MariaDB does not). **Decide from evidence:** open
the Metrics page during a run; if "Waited, mean" on `GET (static files)`
or `GET /api/summary` is tens of milliseconds or more, raise it.

**Three things there is no switch for. Know them before you deploy.**

1. **Anyone who can open a build's page can delete its results.** There is no
   login. The guard is a typed build name and a required reason, checked
   again by the server. If that is not acceptable on your site, do not
   deploy this drop; there is no flag that turns the delete off.
2. **A delete does not block a re-import.** A feeder still sending those
   records puts them back at its next push. Stop the feeder first.
3. **Six route labels changed in the performance log**: `POST
   /api/assignments/*` is now `…/bulk`, and the new endpoints have their own.
   A `--perf-log` file that spans the deploy will show both.

## Deploy

```
sudo systemctl stop testboard        # or however the service is stopped there
cd /opt/testboard && git fetch && git checkout <this drop's commit>
sudo systemctl start testboard
```

**Restart the server — not optional.** Every package here changed Python; a
process that is not restarted will serve the new pages against the old
handlers. The pages were written to survive that (the product list falls
back, the environment filter stays hidden, the comparison ignores a parameter
it does not know) — but the delete, the bulk comment and the Metrics page
will fail, and it will look like a bug. No database step. No feeder step.
Staging (SQLite) and production (MariaDB) take the identical procedure.

## Check it came up

1. The server's start-up output includes `metrics: in memory (84 storage
   methods tallied); see metrics.html`.
2. `What's new` in the nav shows **30 September 2026**; every page's nav has
   **Metrics**.
3. Open **Metrics**. It names the engine (MariaDB on production), schema
   version 10, and lists requests. Press Refresh: `GET /api/metrics` gains
   one to its count and shows 0 storage calls.
4. Open a build. On "Difference from …": the **Environment** box is there;
   choosing one changes every count and adds a line saying which. Switch to
   "Its own results": the same environment is selected.
5. On that tab press **Review** on a row, add a comment: it appears in the
   **Comment on this build** column at once.
6. At the foot of the page: **Delete results from this build…**, collapsed.
   Open it: it lists the build's environments with counts. **Do not test the
   delete on a build you want.**
7. Mainline's Dashboard, Time, Timeline and Watch look as they did.

**In the first hour**, on the Metrics page: "Waited, mean" should be near
zero on every route (a large figure is no free worker, not a slow query); the
memo line's "cleared N times" will climb with every push during a run — that
is the behaviour the performance pass was for, not a fault.

A delete is recorded in the server log, and nowhere else:

```
journalctl -u testboard | grep 'build results deleted'
```

## Roll back

```
sudo systemctl stop testboard
cd /opt/testboard && git checkout <previous commit>
sudo systemctl start testboard
```

Nothing to restore, because nothing in the schema changed. What rolling back
does **not** do: bring back anything deleted with WP-34 (that needs the
database backup), or remove comments posted since the deploy (they are
ordinary comments; the previous build shows them).

  evidence is DOM-shim drivers (scratch, not in the repo) against a server
  booted from the working tree on a seeded copy of the dev estate: **212
  checks** across 13 scenarios — filter 89, delete 47, comments 40, metrics
  36. The shim cannot see layout: whether the new column makes the
  "Difference from" table too wide, how the delete section looks, and
  whether the Metrics tables fit a laptop screen are all unseen.
- **The standing sanity net is not green, and was not before.** It fails 5
  checks on this drop and the same 5 on `master`: its seed is dated August,
  so no build in it has run in the last fortnight. It shows no NEW failure;
  it cannot currently show a pass.
- **Nothing was measured on MariaDB, and nothing on production data.** Every
  timing above is SQLite on a development machine. The changes reduce the
  number of passes and statements, which should help MariaDB at least as
  much — that is an argument, not a measurement. Over HTTP on that machine
  the same request varied 2–3× between runs, which is why the comparison was
  made in-process.
- **The delete at scale on MariaDB.** It has run there on a handful of rows,
  in tests. Which index MariaDB chooses for its per-hour read of `runs` was
  not examined; on SQLite a test pins it. Measured on SQLite: 50 ms for 2,036
  runs, 532 ms for 22,245.
- **A delete while an import is writing.** One transaction on each side; not
  exercised together.
- **The counters under real traffic.** Eight threads in a unit test; never a
  pool under production load.
- **Whether the home page is now fast enough.** The cold headline halved
  here, and the memos now survive most pushes. Production is about four
  times this data and a different engine; the Metrics page is how to find
  out — "Waited, mean" says whether what is left is the pool.
- **WP-38's first paint in a real browser.** The skeleton tiles and the
  module preloads were checked by reading the markup and by the shim; no
  browser has shown whether the frame appears before the scripts load, or
  how long the placeholders stay.
