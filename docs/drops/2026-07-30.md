## What changed, shortest first

**Fixes**

1. **The Time page was broken in production and now works.** It threw
   `formatTime is not defined` and rendered nothing for any estate containing a
   test that had stopped reporting — which is every estate, most days. A missing
   import in `static/time.js`; nothing to do with Python. Two secondary bugs on
   the same page went with it: its hover tooltips were rendering blank values
   (wrong data shape, passed as arrays where every other caller passes
   objects), and it now states how many tests it excluded and since when.

2. **Pages that would not load.** Reproduced, fixed, and pinned by a test.
   A worker serves a whole *connection*, the server speaks HTTP/1.1, and no
   socket timeout was set — so a worker that had answered a request sat
   blocked on an idle keep-alive socket until the browser chose to close it,
   which could be never. Browsers open up to six connections per origin and
   hold them long after they are done, so **two idle tabs could occupy every
   worker in the default eight-worker pool with the server completely idle.**
   That is "the page won't load" with nothing in the logs.
   Measured on the reproduction (two idle connections, two workers): a third
   request waited **5.00s before, 0.24s after**.

**Changes testers will see**

3. **Time page is now a treemap** — the profiler-style box graph, drilling
   environments → scripts → tests, same drill-down as before. Box area is
   strictly its share of the run time (verified: worst drift 0.5 percentage
   points, all of it the 2px gaps between boxes), so nothing small looks big.
   Boxes too small to hold a label say so on the page, and the sortable table
   underneath still lists every row.

4. **"Last update" pills filter the page.** Click an environment to scope
   everything to it, click again to clear. All environments stay listed with
   the active one filled in.

5. **The "What's new" link carries the latest drop's date**, with a dot until
   this browser has opened that drop. Sourced from `whatsnew.html` itself
   (`data-drop-date`), so there is no second copy of the date to go stale — a
   guard test fails the build if the attribute and the heading disagree.

6. **Site-specific notes on the What's new page** — see below; this is the one
   change that needs a decision from you.

**New operator tooling** (nothing user-visible)

7. `tools/drop_environment.py` — delete an environment and everything keyed to
   it, for the `UNKNOWN` rows.
8. `tools/perf_report.py` + `run_server.py --perf-log` — timing to disk, read
   back later, including **how long each connection queued for a worker**.
9. `tools/add_site_note.py` — add/correct/remove this site's own What's new
   notes.

## Upgrade procedure

Nothing here differs from the usual drop except that **no migration runs**.

```bash
# 1. On your machine: confirm what you are shipping.
git log --oneline origin/master..main
python -m unittest discover          # expect 1268 OK (skipped=1)

# 2. Push.
git push origin main:master          # local branch is main, remote is master

# 3. On the server, with the feeder NOT importing:
cd /path/to/testboard
sudo systemctl stop testboard        # or however it is run

cp testboard.db      testboard.db.pre-2026-07-30
cp testboard.db-wal  testboard.db-wal.pre-2026-07-30   # if present
cp testboard.db-shm  testboard.db-shm.pre-2026-07-30   # if present

git pull
sudo systemctl start testboard
```

**The restart is not optional.** Static files are read from disk per request but
the Python is whatever was imported at process start, so a stale process serves
this drop's HTML against the previous drop's handlers. That failure looks exactly
like a UI bug and has cost this project time twice.

### Check it came up

```bash
curl -s localhost:8000/api/summary  | head -c 200      # 200, JSON
curl -s localhost:8000/api/site-notes                  # 200, notes: []
```

In a browser, hard-refresh (Ctrl-Shift-R) and check:

- **Time** page renders a box graph, not an error and not an empty card.
- Clicking a box drills in; the trail at the top walks back out.
- A **"Last update"** pill scopes the page; clicking it again clears it.
- The **What's new** link shows `30 Jul` with a dot beside it.

Then the existing per-drop check, unchanged: each environment reads
`N of N counted` under Open actions → Environment expectations. A `0 of N`
means the cutoff has silently fallen back to the wall clock — set the expected
count before anyone triages.

### Rolling back

```bash
sudo systemctl stop testboard
git checkout <previous-commit>
cp testboard.db.pre-2026-07-30 testboard.db     # only if something wrote badly
sudo systemctl start testboard
```

No schema change means the previous code reads the current database happily.
This is the only drop so far where that is true — do not assume it of the next
one.

## The two new flags, and the decision you need to make

Both are **off unless given**. The drop changes nothing if you ignore them.

### `--perf-log PATH` — catch the next stall

```bash
python3 run_server.py --db testboard.db --perf-log /var/log/testboard-perf.log
python3 tools/perf_report.py /var/log/testboard-perf.log
```

**Recommend turning this on now and leaving it on.** The remaining stalls are
intermittent, and an intermittent fault cannot be caught by logging started
after it happens. It is safe to leave running: capped at 128 MB
(`--perf-max-mb`) and rolled over, so at most 256 MB is ever on disk, and a
full disk degrades to "no records" rather than to errors on the dashboard.

The column that answers the question you actually have is the queue wait:

```
GET /api/summary   n=21  mean 184ms  p50 175ms  p99 221ms   q50 615ms  q99 1.23s
```

Mean 184ms but a median 615ms *waiting for a worker* — that is contention, not
a slow query, and the fix is `--workers` or whatever is holding them. A slow
request with a near-zero queue wait is the opposite diagnosis. Request time
alone cannot tell them apart, which is why the field exists.

### `--site-notes PATH` — your own notes on the What's new page

Default is `site_notes.json` beside the database, so usually nothing needs
saying. Notes live **outside the repository**; `git pull` cannot touch them.

```bash
python3 tools/add_site_note.py --db testboard.db \
    --text "Fixed the parser bug that was filing runs under UNKNOWN."

python3 tools/add_site_note.py --db testboard.db --list          # shows ids
python3 tools/add_site_note.py --db testboard.db --edit 3 --text "Corrected: ..."
python3 tools/add_site_note.py --db testboard.db --remove 3
```

**A note is published the moment you write it** — the file is read per request,
so there is no restart and no review step between typing and every tester
seeing it. That is why `--edit` and `--remove` exist. Check `--list` before and
after.

**The decision:** whether testers should see local notes at all, or whether
this stays an internal record. Nothing appears until you add a note, so
deferring costs nothing.

## Dropping the UNKNOWN environment

Separate from the upgrade — do it whenever, with the server stopped.

```bash
# 1. Look first. Changes nothing.
python3 tools/drop_environment.py --db testboard.db -e UNKNOWN --dry-run

# 2. Take a copy. This cannot be undone.
cp testboard.db testboard.db.before-unknown-drop

# 3. Do it. It asks you to type UNKNOWN back before proceeding.
python3 tools/drop_environment.py --db testboard.db -e UNKNOWN
```

Match is exact and case-sensitive: `UNKNOWN` does not take `unknown` or
`UNKNOWN-2` with it, so run `--dry-run` first and read the row counts. It
covers every table keyed by environment plus the compressed outputs, in one
transaction, ordered so no derived row is ever left pointing at a deleted run.
Re-running it afterwards is quiet and exits 0. Restart the server after.

If the reader is still mis-filing runs, they come back tomorrow night. Fix the
reader first — and consider logging that fix with `add_site_note.py` so the
testers who reported it can see it was done.

## What was NOT verified, and what that means for acceptance

Stated plainly, because the acceptance test is where it gets caught or does not:

- **No browser has rendered any of this.** There is no browser on this machine.
  The frontend was verified by driving the real ES modules against a live
  server under a DOM shim in node: that catches wrong field names, missing
  imports and DOM errors — it is how the `formatTime` bug and a real
  `Array.from` bug in the new code were both found — but **it cannot catch
  layout, colour, contrast or anything about how it looks.** The treemap in
  particular has never been seen by a human eye at a real screen size.
- **Numbers here come from the dev database** (218 MB of generated data,
  540,192 runs) on a developer machine. Production is ~900 MB, roughly four
  times that, on different hardware. The 5.00s → 0.24s figure is from the
  keep-alive reproduction, not from production traffic.
- **The keep-alive fix changes connection handling for every client.** It is
  covered by six new tests including the original reproduction, and the one
  regression it caused during development (connections dropped without a
  response under load) was caught by an existing guard test and fixed. But it
  is the change most worth watching in the first hour.
- `tools/diagnose_db.py --compare-local` has still never been run on the
  production server, so no timing on file describes production hardware.
