## What changed, fixes first

**Fixes** — unchanged from the 2026-08-04 note, section "What changed": the
keep-alive connection bug (a timed-out read poisoned the reader; occasional
failed comment/assignment on a busy dashboard) is fixed and pinned by
deterministic tests.

**The Timeline (WP-18)** — unchanged from the 2026-08-04 note: new page,
`script_hours` derived table (migration 7), test-level stepping, search, deep
links, keyboard access. Read that note's feature section; its content is
absorbed here, not repeated.

**MariaDB support (WP-19)** — the dashboard can now serve from MariaDB:

1. `run_server.py --db-config /etc/testboard/db.cnf --site-notes PATH`
   serves from MariaDB through the vendored driver. Nothing installed,
   nothing built — the checkout still is the deployment.
2. **SQLite is unchanged and permanent.** `--db PATH` behaves byte-for-byte
   as before (the seam commit's proof was the whole suite green with zero
   test edits). A second instance still starts on a file with nothing else
   set up. This drop does NOT move the database — that is the separate §E
   cutover, on your schedule.
3. Flag safety: `--db` and `--db-config` together, `--db-config` without
   `--site-notes`, or SQLite tuning flags (`--cache-mb`/`--mmap-mb`) with
   MariaDB are **refused with the reason**, exit 2, rather than silently
   reinterpreted.
4. On MariaDB the server never runs DDL: it verifies `schema_version`
   equals the build's and refuses both directions. Schema comes from the
   migration tooling only (runbook §D).
5. Search behaviour on MariaDB is deliberately case-insensitive like
   SQLite's; the folding is slightly broader (Unicode case and accents
   fold too, where SQLite folds ASCII only). Nobody should notice; now
   it is written down.

## Upgrade procedure

```bash
# 0. on the deploy box, confirm what you are getting
git fetch && git log --oneline origin/master..origin/wp-18-timeline

# 1. push the drop branch to master (after acceptance sign-off)

# 2. on the server: stop, COPY, pull, start — the copy IS the rollback
systemctl stop testboard        # or however the service is run
cp /path/to/testboard.db      /path/to/backup/testboard.db.pre-2026-08-07
cp /path/to/testboard.db-wal  /path/to/backup/ 2>/dev/null || true
cp /path/to/testboard.db-shm  /path/to/backup/ 2>/dev/null || true
git -C /opt/testboard pull
systemctl start testboard
```

**The restart is not optional.** Static files are read per request; the
Python is whatever was imported at process start. Do the stop/copy/pull/start
when the feeder is not mid-import.

### Check it came up

```bash
journalctl -u testboard | grep "script_hours: rebuilt"   # migration 7 ran
curl -fsS localhost:8000/api/summary >/dev/null && echo summary-ok
curl -fsS "localhost:8000/api/timeline?environment=SOME_ENV" >/dev/null && echo timeline-ok
```

Then in a browser, hard-refresh (Ctrl-Shift-R): the What's new page shows
"7 August 2026"; the Timeline tab exists and loads.

### Rolling back

```bash
systemctl stop testboard
git -C /opt/testboard checkout <previous-master-sha>
cp /path/to/backup/testboard.db.pre-2026-08-07 /path/to/testboard.db
rm -f /path/to/testboard.db-wal /path/to/testboard.db-shm
systemctl start testboard
```

The copy is required: a v7 database is refused by v6 code. Anything imported
between upgrade and rollback is re-imported by the feeder's next push.

  or contrast. The browser pass is the acceptance list.

  a local 12.3 dev install.** The RHEL 8 host's own 10.3.39, socket auth,
  SELinux, and the systemd unit are unexercised until the §E.1 dry run.

  numbers do not exist. The dev-machine MariaDB runs under CPU emulation and
  no number from it will ever be quoted.

- A true 8-hour `wait_timeout` expiry is simulated (a killed session plus a
  compressed clock), not endured overnight.
