The rebuild is the only part of either migration that scales with the
estate rather than being O(1) — it is a full rewrite of `latest_runs` to

cannot add a column into an existing primary key in place). 0.6 s for
12,008 rows on this dev copy; production's `latest_runs` is the same order
of magnitude (one row per test, not per run), so expect a broadly similar
pause, not a multiple of it the way a `runs`-table backfill (migrations 6
and 7) would scale. Watch the log for the `latest_runs: rebuilt N rows with
stream_id in Xs` line — its absence, on a startup that otherwise looks
normal, would mean migration 9 did not run, which would leave `stream_id`
missing and every query that filters on it broken.

## What changed, fixes first

**Fixes:** none. Both packages are pure feature drops.

### WP-20 — products + the Watch page (migration 8)

Unchanged from the original 2026-08-14 note:

1. **Products.** An environment can be declared as belonging to a product
   (`PUT /api/environments/{env}/product`). `product=` is accepted by
   `/api/dashboard`, `/api/summary`, `/api/time` and `/api/timeline`. **A
   deployment with fewer than two declared products sees ZERO visible
   change.**
2. **The header product switcher** (`static/products.js`) — Dashboard, Open
   actions, Time, Timeline, Watch only.
3. **The Product column** on the Dashboard and Open actions tables.
4. **A new page: Watch** (`static/watch.html`) — a URL-configured grid of
   verdict cards (environment, product, and now stream — see below).
5. **New endpoint:** `GET /api/watch`.

### WP-21 — branches and builds beside mainline (migration 9)

The feature `docs/STREAMS_PLAN.md` §3 describes in full; the shape of it:

1. **A "stream" is `(product, kind, name)`** — `kind` is `branch` or
   `build` (mainline is the implicit, un-droppable stream id 1, seeded by
   the migration itself). A record's stream is resolved ONCE, from the
   import batch's `branch`/`build` field, and its product is fixed at that
   moment from the environment's declared product (WP-20) — renaming an
   environment's product afterwards does not retroactively move a stream.
2. **Import contract** (`POST /api/import`): each record MAY carry
   `branch` OR `build` (never both — `400` if a batch does). The response
   gains `streams_seen`: the sorted list of every non-mainline stream that
   batch touched, as `"branch:<name>"`/`"build:<name>"` strings, `[]` for a
   mainline-only batch. **A response with the key ABSENT (not `[]`) is how
   a new feeder detects an old server** — see the feeder section below.
3. **The legacy-UNIQUE collision case.** `runs`' `(environment, script,
   test_name, start_time)` UNIQUE constraint is frozen since migration 1
   and cannot hold two different streams' runs at the exact same instant
   for the exact same test. This is rare (it needs a branch and mainline
   to report the identical test at the identical microsecond) but
   possible, and the record that loses is **rejected, not overwritten** —
   it comes back in the import response as a rejection with an explicit
   message, never silently dropped and never silently filed into the
   wrong stream.
4. **Mainline is provably unaffected.** `activity_hours`/`script_hours`
   (the Timeline's data) only ever accumulate mainline's own runs;
   un-retirement (a retired test's retirement clearing when it reports
   again) only fires for mainline runs — a branch predating a retirement
   must not silently un-retire it; every estate-wide read (the home
   screen, Open actions, the Timeline, `/api/environments`, `/api/scripts`)
   is hardcoded to mainline with no override parameter at all, so there is
   no query string that could accidentally leak a branch's numbers into
   an estate-wide view.
5. **The Build picker** (`static/streams.js`, dashboard toolbar only) —
   hidden unless the current product has at least one branch/build stream.
   Picking one navigates to `?stream=<id>` and swaps the WHOLE dashboard
   body for the **delta view**: five tiles (new failures, new passes, both
   failing, new tests, no result), an "N tests agree and are not listed"
   line, a coverage line ("N of M tests have a result on this branch"),
   both sides' freshness, a stale-baseline warning when mainline itself
   hasn't run recently, and tabbed paginated tables (mainline's result
   ghosted/outlined, the branch's solid). **A mainline page
   (`index.html` with no `?stream=`) never fetches or renders any of
   this — zero visible change**, pinned by a dedicated test.
6. **Test detail** (`?stream=<id>`) scopes the history table and analytics
   to that stream's own runs, and shows a compare strip (mainline's result
   beside the branch's) for the same test. Comments are never filtered by
   the current stream — the whole thread shows, each comment tagged with
   which stream it was posted from (a batch resolve, not one query per
   comment).
7. **The Watchlist gains an `s:` card** — a branch/build verdict card
   (same compare-vs-mainline headline, both sides' freshness), resolved
   through the same batched storage reads `/api/compare` uses so
   `/api/watch` keeps its one-query-per-derived-table property regardless
   of how many stream cards a URL carries.
8. **New endpoints:** `GET /api/streams?product=` (the picker's data),
   `GET /api/compare?stream=&category=` (the five/six counts plus one
   paginated category; `baseline` must be mainline in this drop — cross-
   branch baselines are WP-22).
9. **`tools/drop_stream.py`** — the `drop_environment.py` analogue for a
   typo'd or dead branch/build stream. Refuses mainline unconditionally,
   `--dry-run` first, confirmation prompt unless `--yes`.
10. **Feeder:** new `--branch NAME` / `--build NAME` flags (mutually
    exclusive). A feeder invoked with either **requires** the
    `streams_seen` acknowledgment in the import response and aborts
    loudly (exit 1, no high-water-mark saved) if it is absent — the only
    way an old server can be told apart from one that silently filed
    everything into mainline. Each stream gets its own state file
    (`feeder_state.branch.<name>.json`), so a branch's catch-up run never
    shares — or fights over — mainline's high-water mark.

**Performance:** not separately measured beyond the migration timings
above. Every new estate-wide read stays hardcoded to mainline (no new query
shape there); the delta view's reads are two joins of two `latest_runs`
partitions, bounded by the stream's own product's test count (a few
thousand, not the whole estate's history) — the same shape
`docs/STREAMS_PLAN.md` §3.5 specified and `tests/test_storage.py` pins with
query-count tests.

**Migration registry note:** this drop takes versions **8** (WP-20) and
**9** (WP-21) — `wp-14-in-run-progress`/WP-15's `run_progress` table has
renumbered to **10** to make room, a third time this exact swap has
happened (see `UPGRADE_PLAN.md` §1's note on it). Current in the registry;
saying it here too since whoever merges that branch is more likely to read
the latest drop note.

## Upgrade procedure

**Two migrations run in one restart — same drill as always: the database
copy is the rollback.**

```bash
# 1. On your machine: confirm what you are shipping.
git log --oneline origin/master..wp-21-streams
python -m unittest discover          # expect 1644 OK (skipped=1)

# 2. Push (after acceptance).
git push origin wp-21-streams:master

# 3. On the server, with the feeder NOT importing:
cd /path/to/testboard
sudo systemctl stop testboard

cp testboard.db      testboard.db.pre-2026-08-14          # THE rollback
cp testboard.db-wal  testboard.db-wal.pre-2026-08-14      # if present
cp testboard.db-shm  testboard.db-shm.pre-2026-08-14      # if present

git pull
sudo systemctl start testboard       # first start runs migrations 8 AND 9 — see timings above
```

**The restart is not optional**, as ever: a stale process serves this
drop's `watch.html`/`streams.js`/`compare.js` against handlers that have
never heard of `/api/streams`, `/api/compare`, or `stream=`, and the page
fails in a way that looks exactly like a UI bug rather than a deployment
step skipped.

### Check it came up

```bash
curl -s "localhost:8000/api/summary?parts=headline" | head -c 200   # 200, JSON, has "products"
curl -s "localhost:8000/api/watch" | head -c 100                    # 200, {"cards": [], "cap": 50}
curl -s "localhost:8000/api/streams?product=" | head -c 100         # 200, {"product": "", "streams": []}
curl -s -o /dev/null -w '%{http_code}\n' localhost:8000/watch.html  # 200
```

In a browser, hard-refresh (Ctrl-Shift-R) and check:

- Every page still looks exactly as it did before this drop — no switcher,
  no Product column, no Build picker, no branch band, EXCEPT the "Watch"
  nav entry (deliberately never hidden — environment cards work with zero
  products declared).
- Open the Watch page bare: it shows the "add a card" how-to, not a blank
  page or an error. Add an environment card and a product card, confirm
  the existing WP-20 behaviour is unchanged.
- Feed one test's results in under `--branch some-test-branch` (or a raw
  `POST /api/import` with a `branch` field on one record). Confirm:
  - the import response carries `"streams_seen": ["branch:some-test-branch"]`;
  - the Build picker appears on the dashboard for that product;
  - picking it shows the delta view — tiles, tabs, the agree/coverage
    lines, both freshness timestamps;
  - the mainline dashboard is completely unaffected (same numbers as
    before the branch import);
  - a Watchlist `s:` card for that stream renders a verdict.
- `tools/drop_stream.py --db testboard.db --product <p> --kind branch --name some-test-branch --dry-run`
  reports the row counts without changing anything; without `--dry-run` it
  prompts for confirmation and removes the stream cleanly, leaving mainline
  untouched.

### Rolling back

```bash
sudo systemctl stop testboard
git checkout <previous-commit>
cp testboard.db.pre-2026-08-14 testboard.db           # REQUIRED, not optional:
cp testboard.db-wal.pre-2026-08-14 testboard.db-wal   # v7 code REFUSES a v8/v9 file
sudo systemctl start testboard
```

Anything imported between upgrade and rollback (mainline or a branch) is in
the file you just put aside, not the one you restored — re-run the feeder
for the gap (safe: the server upserts).

## What was NOT verified

- **No browser has rendered any of this drop — WP-20 or WP-21.** This is
  still true, and is still the biggest unverified surface of any drop so
  far. What changed from a typical drop note: this session went further
  than the usual static-analysis-plus-curl pass, and it is worth saying
  exactly how far, because it changes what the acceptance list below still
  needs a human for.
  - **Static analysis** of the actual `.js` source
    (`tests/test_frontend_calls.py`) — the usual method, no JavaScript
    runtime here and none is planned.
  - **A real server, real data, real HTTP.** A scratch copy of the dev
    database was fed an actual branch import (`POST /api/import` with
    `branch` set, against a `linux-sim` test that already had mainline
    history) through a running `run_server.py`, then driven end to end
    with `curl` and small Python scripts: `streams_seen` in the import
    response, `/api/streams`, `/api/compare`, the comments endpoint's new
    `streams` map, and `tools/drop_stream.py --dry-run` against the
    result.
  - **The actual frontend JavaScript, executed, against that same live
    server.** The project's existing node DOM-shim harness (`.scratch/`,
    gitignored — used previously for `timeline.js` and `app.js`'s product
    switcher) was extended (`location.search`/`.pathname`, previously
    absent) and driven through four new scenarios, each asserting on the
    real DOM tree `app.js`/`test.js`/`watch.js` actually built from the
    real server's real JSON:
    1. A bare `index.html` load — confirmed **zero fetches to
       `/api/compare`**, `branch-band`/`delta-section` stay hidden, the
       ordinary mainline sections render, matching the source-level
       zero-visible-change guard test.
    2. `index.html?stream=<id>` — confirmed the mainline sections hide,
       the branch band names the stream, all five tiles render with
       correct counts, the agree/coverage/baseline lines carry real text
       built from the response, the five tabs render, and the
       `new_failures` tab's default page shows the actual failing test.
    3. `test.html?...&stream=<id>` — confirmed the compare strip shows
       (mainline's PASS beside the branch's FAIL for the same test), the
       page's own "latest" is the branch's result, and a comment posted
       from that view carries a "posted from branch …" tag.
    4. `watch.html?c=s:<id>` — confirmed the card renders (not an error
       card), names the stream and its kind, and its "Open in
       dashboard →" link lands on `index.html?stream=<id>`.

    **This caught two real defects before they shipped**, neither visible
    to any unit test because every unit test that exercises a stream also
    calls `set_environment_product` first: (a) `test.js` never actually
    rendered a comment's "posted from" tag — the backend's batch-resolved
    `streams` map existed but nothing on the frontend read it, fixed by
    wiring `commentNode()`/`loadComments()`/`onCommentSubmit()` to use it
    and tag/stamp comments correctly; (b) the Watchlist's `s:` card was
    **silently all-zero for any stream whose product is `""`** — the
    common case on a deployment that has never declared a product at all
    (WP-20's default shape) — because `_handle_watch` resolved a stream's
    environment scope through `product_to_envs.get("", [])`, which is
    *always* empty (`environment_products_map()` only lists environments
    that HAVE a declared product), instead of the "every known
    environment nobody has mapped" rule
    `Storage.environments_for_product("")` already used correctly on the
    single-stream `/api/compare` path. Fixed in `_handle_watch`
    (still O(1) queries), pinned by
    `tests/test_api.py::TestWatchStreamCardImplicitProduct`.
  - What none of this proves: layout, the Build picker's visual placement
    in the toolbar, the branch band's legibility or contrast, whether the
    compare strip reads cleanly at a real screen width, or whether five
    tiles plus a tabbed table plus a compare table is too much page for
    one screen. The shim has no CSS and no eyes — it proves wiring and
    data flow, nothing about how it looks.
- **The dual-backend (MariaDB) suite has run against the dev machine's
  local `mariadbd`** (port 3307, `.scratch/mariadb-test.cnf`, a
  sacrificial database) — **2152 green (skipped 16)**, on the FINAL tree,
  after the two fixes above. **Still not done from here:** this is the dev
  machine's local MariaDB,
  not CI's `mariadb:10.3` service and not production's server — CI's
  `python36-mariadb` leg on this branch has not been observed, only the
  local equivalent.
- **Production numbers are projections.** Every timing in this note is
  from the 220 MB dev copy; production is roughly 4x that on a network
  mount and has not been measured from here. Migration 9's rebuild is the
  one part of this drop whose cost scales with estate size (one row per
  test, not per run) — worth re-measuring on a production copy before
  shipping if the acceptance list below has not already forced that.
- **The legacy-UNIQUE collision path** (docs/STREAMS_PLAN.md §3.2) is unit
  tested on both backends but has never been provoked against a real feed
  — it needs a branch and mainline reporting the identical test at the
  identical microsecond, which no dev or demo data naturally produces.
