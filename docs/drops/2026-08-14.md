### WP-21 — branches and builds beside mainline (migration 9)

The feature `docs/STREAMS_PLAN.md` §3 describes in full; the shape of it:

1. **A "stream" is `(product, kind, name)`** — `kind` is `branch` or
   `build` (mainline is the implicit, un-droppable stream id 1, seeded by
   the migration itself). A record's stream is resolved ONCE, from the
   import batch's `branch`/`build` field, and its product is fixed at that
   moment from the environment's declared product (WP-20) — renaming an
   environment's product afterwards does not retroactively move a stream.
2. **Import contract** (`POST /api/import`): each record MAY carry
   `branch` OR `build` (never both — `400` if a batch does). The response
   gains `streams_seen`: the sorted list of every non-mainline stream that
   batch touched, as `"branch:<name>"`/`"build:<name>"` strings, `[]` for a
   mainline-only batch. **A response with the key ABSENT (not `[]`) is how
   a new feeder detects an old server** — see the feeder section below.
3. **The legacy-UNIQUE collision case.** `runs`' `(environment, script,
   test_name, start_time)` UNIQUE constraint is frozen since migration 1
   and cannot hold two different streams' runs at the exact same instant
   for the exact same test. This is rare (it needs a branch and mainline
   to report the identical test at the identical microsecond) but
   possible, and the record that loses is **rejected, not overwritten** —
   it comes back in the import response as a rejection with an explicit
   message, never silently dropped and never silently filed into the
   wrong stream.
4. **Mainline is provably unaffected.** `activity_hours`/`script_hours`
   (the Timeline's data) only ever accumulate mainline's own runs;
   un-retirement (a retired test's retirement clearing when it reports
   again) only fires for mainline runs — a branch predating a retirement
   must not silently un-retire it; every estate-wide read (the home
   screen, Open actions, the Timeline, `/api/environments`, `/api/scripts`)
   is hardcoded to mainline with no override parameter at all, so there is
   no query string that could accidentally leak a branch's numbers into
   an estate-wide view.
5. **The Build picker** (`static/streams.js`, dashboard toolbar only) —
   hidden unless the current product has at least one branch/build stream.
   Picking one navigates to `?stream=<id>` and swaps the WHOLE dashboard
   body for the **delta view**: five tiles (new failures, new passes, both
   failing, new tests, no result), an "N tests agree and are not listed"
   line, a coverage line ("N of M tests have a result on this branch"),
   both sides' freshness, a stale-baseline warning when mainline itself
   hasn't run recently, and tabbed paginated tables (mainline's result
   ghosted/outlined, the branch's solid). **A mainline page
   (`index.html` with no `?stream=`) never fetches or renders any of
   this — zero visible change**, pinned by a dedicated test.
6. **Test detail** (`?stream=<id>`) scopes the history table and analytics
   to that stream's own runs, and shows a compare strip (mainline's result
   beside the branch's) for the same test. Comments are never filtered by
   the current stream — the whole thread shows, each comment tagged with
   which stream it was posted from (a batch resolve, not one query per
   comment).
7. **The Watchlist gains an `s:` card** — a branch/build verdict card
   (same compare-vs-mainline headline, both sides' freshness), resolved
   through the same batched storage reads `/api/compare` uses so
   `/api/watch` keeps its one-query-per-derived-table property regardless
   of how many stream cards a URL carries.
8. **New endpoints:** `GET /api/streams?product=` (the picker's data),
   `GET /api/compare?stream=&category=` (the five/six counts plus one
   paginated category; `baseline` must be mainline in this drop — cross-
   branch baselines are WP-22).
9. **`tools/drop_stream.py`** — the `drop_environment.py` analogue for a
   typo'd or dead branch/build stream. Refuses mainline unconditionally,
   `--dry-run` first, confirmation prompt unless `--yes`.
10. **Feeder:** new `--branch NAME` / `--build NAME` flags (mutually
    exclusive). A feeder invoked with either **requires** the
    `streams_seen` acknowledgment in the import response and aborts
    loudly (exit 1, no high-water-mark saved) if it is absent — the only
    way an old server can be told apart from one that silently filed
    everything into mainline. Each stream gets its own state file
    (`feeder_state.branch.<name>.json`), so a branch's catch-up run never
    shares — or fights over — mainline's high-water mark.
11. **Four findings from the first human use of the branch dashboard**,
    added to this same unshipped drop rather than deferred:
    - **The branch band now also shows on the test-detail page**
      (`?stream=<id>`), not only the dashboard — sharing one
      `renderBranchBand()` function, not a second implementation. A
      reader who clicked through from the delta table into a test's own
      page previously lost every indication they were scoped to a
      branch at all; the compare strip alone was not loud enough.
      "Back to mainline" is now the current URL with only `stream`
      stripped, computed the same way on both pages, so the test page's
      link correctly preserves `environment`/`script`/`test_name`
      instead of bouncing to a fixed `index.html`.
    - **Triage from a branch actually works now.** The delta table's
      rows carry the same assignee select and inline Review expander
      (captured output, "View in timeline", a comment box) as every
      other list in the app — item 4 above ("mainline is provably
      unaffected") is unchanged: this reads/writes the (environment,
      script, test_name) triple's ONE assignee, never a stream-scoped
      copy of it. Retirement is refused by construction on a branch row
      (the shared review panel is simply never told a staleness
      cutoff there, so its own gate never opens) — retirement stays a
      mainline-only decision. `/api/compare`'s paginated rows gained
      `stream_run_id`/`stream_start_time` (the branch's own run; null
      exactly when there is nothing on that side to review — no new
      query shape, both already live on `latest_runs`) and `assignee`
      (the triple's current, unpartitioned owner).
    - **Assignment origin is now recordable** — `assignments`/
      `current_assignments` both gained a nullable `stream_id`
      (**folded into THIS drop's migration 9**, not a new migration 10:
      migration 9 was still unshipped when this was found, so no
      database anywhere has the narrower shape it had before the fold —
      see the entry's own comment in `storage.py` for the reasoning).
      `PUT .../assignee` accepts an optional `stream_id`; every existing
      caller that never sends it is completely unaffected.
    - **Open actions shows where an assignment came from.** A row whose
      current assignment carries a non-mainline stream gets a small
      "branch feat/x" tag (batch-resolved per page, the same pattern
      the comments endpoint uses), and — only once at least one
      assignment anywhere carries a stream — a branch-vs-mainline
      filter chip pair next to the existing owner filters. Both are
      genuinely new query surface on `/api/dashboard`
      (`origin=branch`/`origin=mainline`, server-side, same rule the
      existing owner filter already follows) and `/api/summary`
      (`assignment_streams`, the existence signal). Zero visible
      change on any install where no assignment has ever carried a
      stream.

    Verified beyond the source-level guard tests: a scratch server was
    driven through all four scenarios via the node DOM-shim harness
    (extended further this pass — `insertBefore`/`nextSibling`/
    `remove()`, `document.createDocumentFragment()`, and a `find()`
    guard against text-node leaves, none of which any prior session had
    exercised) — the assignee select showed a REAL pre-existing
    assignee rather than defaulting to "Unassigned" (the specific
    failure mode a wrong payload would produce and still look correct
    at a glance), the Review panel opened onto the branch's own
    captured output, no retire control appeared anywhere, the
    test-page band and its back-link were both correct, and the Open
    actions filter/tag round-tripped a real assignment end to end
    including the server-side re-fetch on a filter click.

### WP-22 — release builds + compare-any-two (no migration)

The feature `docs/STREAMS_PLAN.md` §4 describes in full — RCs and release
builds are the same mechanism as branches (`kind='build'`), read
differently: judged against the build before it, re-cut under the same
name, and comparable directly instead of only via mainline.

1. **`GET /api/compare`'s `baseline=` accepts any stream of the SAME
   product**, not only mainline — a build judged against the build before
   it, or one branch against another. Mainline stays the one universal
   exception on either side of the comparison (its `product` is `''` by
   construction, shared by every product). A baseline from a DIFFERENT
   product is refused with a clear 400 naming both — nothing joins across
   products, since they don't share environments.
2. **The Build picker's Builds group**, newest first by `last_seen` —
   version strings are opaque and never parsed (decision §0.7), so recency
   is the only ordering that means anything.
3. **The build-scoped dashboard gains a "Compare to" box**: a plain
   text-with-suggestions field defaulting to the build's own predecessor
   (by `last_seen`) when one exists, else mainline. Picking a different
   build or branch of the same product re-scopes the comparison via
   `?baseline=<id>` — a real navigation, sharable by URL like everything
   else in this feature. A build's page also says when it was built and
   whether anything has run since.
4. **New: `GET /api/tests/{env}/{script}/{test}/streams`** — a triple's
   latest result on every stream that has one, newest first. Powers two
   new pieces on the test page: the **"Every build" disclosure** (this
   test's latest result on every stream of its product, including the
   ones that never ran it, marked plainly as NO RESULT rather than left
   off the table) and a **stream switcher** near the top of the page — the
   specific thing asked for after first human use of WP-21's branch
   dashboard — jumping straight to this test's result on any other stream
   that has one.
5. **The Watchlist's `s:` card works for builds too**: "N tests failing in
   `<name>`", compared against its predecessor build when one exists (the
   same default the dashboard box uses), falling back to mainline
   otherwise. Every place that used to say the literal word "mainline" —
   the delta view's heading, column headers, freshness lines, the branch
   band, this card — now names whatever the ACTUAL baseline is, since it
   is routinely a predecessor build rather than mainline once this ships.
6. **Verified, not merely assumed:** a build rebuild (a second import
   under the same `build` name) was checked end to end — same stream, no
   duplicate, the newer run wins as "latest", the older run still shows in
   history. The plan's own "superseded runs render as ghosts" line is
   **not literally true today**: the history table draws every row
   solid, with no ghost styling — said plainly here rather than left to
   be discovered later.

**Performance:** not separately measured beyond the migration timings
above (WP-22 itself adds no migration). Every new estate-wide read stays
hardcoded to mainline (no new query shape there); the delta view's reads
are two joins of two `latest_runs` partitions, bounded by the stream's own
product's test count (a few thousand, not the whole estate's history) —
the same shape `docs/STREAMS_PLAN.md` §3.5/§4.1 specified and
`tests/test_storage.py` pins with query-count tests, including the new
per-stream-baseline path `compare_counts_many` gained for WP-22's build
cards.

### WP-23 — long-running branch streams get their own dashboard (migration 10)

The feature `docs/STREAMS_PLAN.md` §5 describes in full; the shape of it —

1. **A long-running branch reads like its own small testboard.** Open a
   branch with a regular nightly cadence and two tabs appear above the
   usual toolbar: **Its own results** (the same tiles, trend chart and
   triage queues the home screen shows, scoped to that branch's own
   runs) and **Difference from mainline** (WP-21/22's delta view,
   unchanged). Both tabs always exist for a branch; the caption under
   them states which one opened by default and why, from data — "this
   branch has completed 8 passes in the last 14 days (2 or more shows
   its own dashboard first)". Release builds keep the WP-21/22
   delta-only view; the two-tab header is a branch concept only.
2. **`activity_hours`/`script_hours` are maintained for every stream
   now**, not only mainline's (the WP-21 skip is gone) — migration 10
   widens both tables' PRIMARY KEY to lead with `stream_id`. Mainline's
   own numbers are unaffected either way: a dedicated guard imports a
   branch into the SAME environment mainline uses and asserts the
   unscoped `/api/summary`/`/api/time`/`/api/timeline` responses are
   byte-identical before and after.
3. **The Time and Timeline pages accept `stream=`** (an id, default
   mainline) — a branch's own running order and where its own suite
   spent its time, read through the same pages mainline already uses.
4. **The comparison view states drift, not just a raw count**: "Of N
   tests failing here, M also fail on mainline too" — separating a
   branch's own regressions from failures it inherited. "Behind by N
   commits" is confirmed, again, as not built (not knowable without VCS
   integration).
5. **The Watchlist's `s:` card is unchanged** — a deliberate decision,
   not an oversight, recorded in `static/watch.js`'s own comment: the
   card is already full, and giving it a branch's own numbers would
   need per-stream pass-detection work `/api/watch`'s O(1)-per-card
   architecture has no batched form of. Open the branch's own dashboard
   tab instead.
6. **New response fields, no contract break**: `/api/summary`,
   `/api/time`, `/api/timeline` all gained an optional `stream=`
   (default mainline — every existing caller unaffected) and echo which
   stream answered; `/api/summary` also gained `covered_passes`, the
   number the two-tab header's caption is built from.

**Performance:** the "own results" tab costs the same query shapes
`/api/summary`/`/api/time`/`/api/timeline` already had, filtered by an
extra `stream_id =` (an indexed column, leading every relevant PRIMARY
KEY) — no new query shape, no new table scan. `tests/test_storage.py`'s
existing query-count/query-plan tests were not weakened to accommodate
this.
