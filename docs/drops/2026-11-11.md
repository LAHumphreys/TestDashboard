## What changed

**New — WP-44: mark a test as flaky.**

A developer marks a test with a reason and a cadence of 2 to 10: "fail if the
N most recent runs fail". While the marked test fails fewer times in a row
than its cadence it is **flaking**: taken off the failing figures and out of
New failures and Still failing, listed in its own Flaking tab, shown as
FLAKING in its own muted colour (a mauve), and named beside the figure it
was taken out of ("+4 flaking"). Flaking is not a pass;
it still counts against the pass rate. The night the test fails past its
cadence it is a new failure again, red, listed in New failures as
FLAKING → FAIL. A mark covers mainline and every build of the test's
environment; its state is worked out per stream.

Where it shows:

- **Marking.** The selection bar (a Flaky group after Mute: Mark as flaky,
  Set cadence, Unmark), the Review panel, and the header of the test's own
  page, beside the Mute offer: "Flaky" and a "Mark as flaky" button on any
  unmarked test, passing or failing, which opens a reason and a cadence; once
  marked, the same place shows the mark with Set cadence and Unmark. The
  page's Flakiness card links to that form, and "Flaky mark history" lists
  every act. The reason is posted as a comment on the test.
- **Home.** The failing figures name what is set aside; "All clear" gains
  "Set aside: N muted · N flaking"; the three charts draw flaking as its own
  part after muted; a **Flaking** tab in Triage lists the tests flaking now,
  nearest to their cadence first, each with its streak ("2 in a row, failing
  at 3"). It is a triage queue like New failures and Still failing: the same
  Output column, Review panel and acts on every row. It is drawn only where
  something is flaking. No page lists every mark: a marked test that passes,
  or fails past its cadence, carries a "flaky" tag on its row and on its own
  page.
- **All tests.** A **FLAKING** filter beside FAIL, shown once a test in view
  is marked. FAIL then leaves the flaking tests out; the two together are
  every failing test.
- **Open Actions.** Unassigned flaking tests are left out until they fail
  past their cadence, and a line under the count says so. An assigned one
  stays, reading FLAKING. **Its Failing mode now leaves them out too**: with
  marks it lists fewer rows than before (162 against 169 on the reference
  seed with 50 marks); with no marks, the same rows.

The computed signal that was worded "flaky — flips about 1 run in 3" now
reads "flips about 1 run in 3" ("flips often" elsewhere), so that on screen
"flaky" always means a mark somebody made.

**Changed for everyone, marks or not — the per-day chart's split arrives one
request later.** Home's first batch is three data requests where it was four:
the headline, the active queue and the browse page. The chart's split
(`parts=assigned_trend`) is sent once the headline has been drawn. On a first
load the chart draws its totals, dimmed, then the split; on a Reload or a
change of scope the previous chart stays dimmed until the new split lands;
after an act the tiles update first and the chart follows. Nothing else on
the page waits for it.

For the operator, the API:

1. `POST /api/flaky/bulk` and `POST /api/flaky/unmark`: the acts.
2. `GET /api/summary?parts=queue&queue=flaking`: the Flaking tab's rows, an
   ordinary queue, asked for when the tab is opened and by no first paint.
   There is no `GET /api/flaky`.
3. `GET /api/summary?parts=names`: the catalogue alone. **Open Actions now
   asks for this and no longer for the full summary**, so its first paint is
   faster (below). One consequence: Open Actions no longer warms Home's
   headline, so Home opened straight after it pays its own cold headline.
4. `flaky` on browse, queue and Open Actions rows and on test detail;
   `flaking` counts on the summary (`status`, `by_environment`, `products`,
   `top_failing_scripts`) and on Watch's cards.
5. `result=FLAKING` on `GET /api/dashboard`, and `result=FAIL` narrowed to
   the FAIL rows that are not flaking; `FAIL_FLAKING` on every night of
   `parts=assigned_trend`.

The README's "Flaky marks" section has the shapes.

## Deploy

Production (MariaDB). The schema moves only by the tool; the app never runs
DDL and refuses a version mismatch in both directions. Order matters.

```
# 1. Credentials per runbook G.1 (the migrate account; delete it at the end).
# 2. G.2 -- the dump IS the rollback. Check it is not tiny.
mysqldump --defaults-file=~/.testboard-migrate.cnf \
    --single-transaction --routines --triggers testboard \
    > testboard-preupgrade-$(date +%Y%m%dT%H%M%S).sql
ls -l testboard-preupgrade-*.sql

# 3. Get the new code onto disk but do NOT restart yet (the tool is in it):
cd /opt/testboard && git fetch && git checkout <this drop's commit>

# 4. Dry run. It runs nothing. READ the SERVER line:
python3 tools/upgrade_mariadb_schema.py upgrade \
    --config ~/.testboard-migrate.cnf --dry-run
```

Expected: `SERVER: may keep running` (the step only creates), with one step,
11 to 12, two `CREATE TABLE` statements and one `CREATE INDEX`, no
`ALTER TABLE`. **If it says `SERVER: STOP IT FIRST`, do what it says**
(`sudo systemctl stop testboard`) — that would mean the ledger changed after
this note was written.

```
# 5. Upgrade (the server may still be running). It verifies by itself:
python3 tools/upgrade_mariadb_schema.py upgrade \
    --config ~/.testboard-migrate.cnf
#    Every table must report "matches the v12 oracle". Any mismatch: do NOT
#    start the new code; restore from the dump (G.2).

# 6. The restart -- NOT optional: Python changed, and the old process
#    would refuse the new schema at its next start anyway.
sudo systemctl stop testboard        # if still running
sudo systemctl start testboard

# 7. Delete the migrate account and ~/.testboard-migrate.cnf (G.1).
```

A SQLite deployment (none is in service) would stop, copy the `.db` aside
(the copy is the rollback), pull, start; the file migrates on open.

**Anyone with an Open Actions page open across the deploy should reload
it.** The page's requests changed (the names part in place of the full
summary; the Failing mode's parameters). An old page against the new server
still loads, with no footer line; once a mark exists its Failing mode would
also drop the flaking tests somebody is assigned to, which the new page
keeps.

Feeders: nothing to stop or deploy. Expect replay resends in feeder logs for
the hour around the restart; count nothing as missing until a run has
pushed since.

## Check it came up

1. Metrics page: schema version **12**. If the server will not start with a
   schema message, the upgrade did not run: that is the upgrade tool's job;
   do not edit `schema_version` by hand to get past it.
2. `curl -s '<base>/api/summary?parts=names'` answers 200 with
   `"flaky_marks": false` (no marks yet).
3. Home looks as it did, with no marks: no flaking figure, no Flaking tab, no
   FLAKING filter on All tests. Two things differ on a board with no marks:
   "All clear" reads "Set aside: N muted" where muted failures exist, and
   the per-day chart gains its split a moment after the rest of the page.
4. Mark ONE failing test you can spare (tick its row, the selection bar's
   Flaky group: a cadence, a reason, Mark as flaky). If it has failed fewer
   times in a row than the cadence, its row reads FLAKING, the failing
   figure drops by one and names "+1 flaking", and the Flaking tab appears
   in Triage with the test in it, its Streak cell reading how many runs in a
   row it has failed against the cadence. Its row has the Review button of
   every other tab: the panel shows the run's output and, under Flaky, the
   mark with Set cadence and Unmark. The test page shows the mark, its
   sentence and its history; the test has one new comment with your reason.
   (If the test has already failed as many times in a row as the cadence, it
   stays where it was, in New failures or Still failing, with a "flaky" tag:
   that is the mark working, not a fault.)
5. All tests now shows a FLAKING toggle beside FAIL; pressed alone it lists
   that test. Open Actions loads; if the test is unassigned it is not on the
   page, and the line under the count says flaking tests are left out.
6. Unmark it (the same bar, or Review on its row in the Flaking tab): the
   counts go back and the test returns to New failures or Still failing; the
   tab goes once nothing is flaking, and the toggle once no mark is left in
   view.

## Roll back

**Old code does not run against a v12 database.** SQLite refuses a newer
schema version at open; MariaDB refuses a mismatch in either direction.
Either restore the dump (G.2), or:

```
sudo systemctl stop testboard
mysql ... -e "DROP TABLE test_flaky_marks, flaky_mark_history; UPDATE schema_version SET version = 11;"
cd /opt/testboard && git checkout <previous commit>
sudo systemctl start testboard
```

(use the migrate credential; the `UPDATE` is the statement the tool itself
writes, with the version lowered; runbook G.6 names the same two tables.) Both
are clean **only until the first mark is written after the restart**: marks
and their history exist only in the upgraded database, and dropping the two
tables takes every mark with them. The comments the marks posted stay, as
ordinary comments. SQLite: restore the copy taken before the start.

## What was NOT verified

- **No real browser has rendered any of this**, as with every drop here, and
  none has rendered the new UI at all. It was walked with a DOM shim, and the
  pages and the API were read over HTTP on a seeded copy, where the Flaking
  tab's total, the FLAKING filter's total and the headline's figures agreed.
  How the mauve reads against the red and the grey, the selection bar's Flaky
  group, the Flaking tab and the chart's fourth part are unseen: the first
  look after deploy is the check.
- **The Flaking tab's rows are read by key, and CI has run that read's plan
  guard on production's stream**: both MariaDB 10.3 jobs read the rows by the
  full primary key. The same guard caught the SQLite of the Python 3.6.8
  target (3.26) reading the whole stream for the same statement, and for
  Open Actions' rows, which had the fault since the first build; on SQLite
  the read is now written so that its plan does not depend on the version,
  and the 3.6.8 jobs pass. No SQLite deployment is in service. One thing is
  stated nowhere and matters only to one: the code needs SQLite 3.15 or
  newer.
- **MariaDB was measured on a local 12.3**; production's 10.3 is exercised
  only by CI. Plans were read by hand on the newer server. One term (the
  FLAKING filter's row-value range) is version-sensitive; its fallback reads
  the stream's failing rows (171 on the seed).
- **The headline's cost is over the bar the design set**, where marks exist:
  by 4 to 7 points of base on SQLite, and at the bar within its band on
  MariaDB (the first table above). It was accepted in the build for the
  owner to confirm. The cheaper shapes were priced and each costs more than
  it saves.
- **The per-day chart's split with many marks is the owner's open decision;
  nothing for the operator to do.** With marks the part reads the marked
  tests' runs night by night: about +8.5 ms at 50 marks and +85 to +164 ms
  at 1,000 on the 7-night seed; on the 90-night seed, 90 days at 1,000 marks,
  +909 to +1,047 ms on a base of 57 to 65, against the 366 ms the design had
  recorded as its worst. It is off first paint as of this drop, so the chart's
  split lands late and nothing else waits. A covering index on `runs` would
  cut it to about 400 ms, for a migration, 23% more database and about 12%
  on a push: priced, not taken. It belongs with the same question left open
  by the previous drop for many assignments.
- **One reading is unexplained:** Home as a page on the local MariaDB with
  no marks read +9.6 ms (9%) against the base in one order and -10.3 ms with
  the sides swapped, with equal statements and every request alone inside
  its band. SQLite shows nothing and it does not grow with marks. It reads
  as an artefact of the measurement on a busy machine and has not been
  repeated on a quiet one.
- **Known and left:** if a Reload's headline request fails while the chart's
  split is on screen, the chart keeps its old bars under the error banner
  until the next Reload.
- Nothing was measured on production's data; every figure is on generated
  development data at production's scale. MariaDB was not measured on the
  90-night seed.
