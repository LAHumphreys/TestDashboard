## What changed

**New — WP-44: mark a test as flaky.**

A developer marks a test with a reason and a cadence of 2 to 10: "fail if the
N most recent runs fail". While the marked test fails fewer times in a row
than its cadence it is **flaking**: set aside from the failing figures and
from triage, shown as FLAKING in its own muted colour (a mauve), and named
beside the figure it was taken out of ("+4 flaking"). Flaking is not a pass;
it still counts against the pass rate. The night the test fails past its
cadence it is a new failure again, red, listed in New failures as
FLAKING → FAIL. A mark covers mainline and every build of the test's
environment; its state is worked out per stream.

Where it shows:

- **Marking.** The selection bar (a Flaky group after Mute: Mark as flaky,
  Set cadence, Unmark), the Review panel and the test page (a banner, the
  Flakiness card and "Flaky mark history"). The reason is posted as a comment
  on the test; every act is in the mark's history.
- **Home.** The failing figures name what is set aside; "All clear" gains
  "Set aside: N muted · N flaking"; the three charts draw flaking as its own
  part after muted; a **Flaky** tab beside Muted lists every mark with its
  reason, owner, cadence and "6 of its last 20 runs".
- **All tests.** A **FLAKING** filter beside FAIL, shown once a test in view
  is marked. FAIL then leaves the flaking tests out; the two together are
  every failing test.
- **Open Actions.** Unassigned flaking tests are left out until they fail
  past their cadence, and a line under the count says so. An assigned one
  stays, reading FLAKING. **Its Failing mode now leaves them out too**: with
  marks it lists fewer rows than before (162 against 169 on the reference
  seed with 50 marks); with no marks, the same rows.

The computed signal that was worded "flaky — flips about 1 run in 3" now
reads "flips about 1 run in 3" ("flips often" elsewhere), so that on screen
"flaky" always means a mark somebody made.

**Changed for everyone, marks or not — the per-day chart's split arrives one
request later.** Home's first batch is three data requests where it was four:
the headline, the active queue and the browse page. The chart's split
(`parts=assigned_trend`) is sent once the headline has been drawn. On a first
load the chart draws its totals, dimmed, then the split; on a Reload or a
change of scope the previous chart stays dimmed until the new split lands;
after an act the tiles update first and the chart follows. Nothing else on
the page waits for it.

For the operator, the API:

1. `POST /api/flaky/bulk` and `POST /api/flaky/unmark`: the acts.
2. `GET /api/flaky`: the Flaky tab's list, asked for on the tab's first
   click and by no first paint.
3. `GET /api/summary?parts=names`: the catalogue alone. **Open Actions now
   asks for this and no longer for the full summary**, so its first paint is
   faster (below). One consequence: Open Actions no longer warms Home's
   headline, so Home opened straight after it pays its own cold headline.
4. `flaky` on browse, queue and Open Actions rows and on test detail;
   `flaking` counts on the summary (`status`, `by_environment`, `products`,
   `top_failing_scripts`) and on Watch's cards.
5. `result=FLAKING` on `GET /api/dashboard`, and `result=FAIL` narrowed to
   the FAIL rows that are not flaking; `FAIL_FLAKING` on every night of
   `parts=assigned_trend`.

The README's "Flaky marks" section has the shapes.

## Deploy

Production (MariaDB). The schema moves only by the tool; the app never runs
DDL and refuses a version mismatch in both directions. Order matters.

```
# 1. Credentials per runbook G.1 (the migrate account; delete it at the end).
# 2. G.2 -- the dump IS the rollback. Check it is not tiny.
mysqldump --defaults-file=~/.testboard-migrate.cnf \
    --single-transaction --routines --triggers testboard \
    > testboard-preupgrade-$(date +%Y%m%dT%H%M%S).sql
ls -l testboard-preupgrade-*.sql

# 3. Get the new code onto disk but do NOT restart yet (the tool is in it):
cd /opt/testboard && git fetch && git checkout <this drop's commit>

# 4. Dry run. It runs nothing. READ the SERVER line:
python3 tools/upgrade_mariadb_schema.py upgrade \
    --config ~/.testboard-migrate.cnf --dry-run
```

Expected: `SERVER: may keep running` (the step only creates), with one step,
11 to 12, two `CREATE TABLE` statements and one `CREATE INDEX`, no
`ALTER TABLE`. **If it says `SERVER: STOP IT FIRST`, do what it says**
(`sudo systemctl stop testboard`) — that would mean the ledger changed after
this note was written.

```
# 5. Upgrade (the server may still be running). It verifies by itself:
python3 tools/upgrade_mariadb_schema.py upgrade \
    --config ~/.testboard-migrate.cnf
#    Every table must report "matches the v12 oracle". Any mismatch: do NOT
#    start the new code; restore from the dump (G.2).

# 6. The restart -- NOT optional: Python changed, and the old process
#    would refuse the new schema at its next start anyway.
sudo systemctl stop testboard        # if still running
sudo systemctl start testboard

# 7. Delete the migrate account and ~/.testboard-migrate.cnf (G.1).
```

A SQLite deployment (none is in service) would stop, copy the `.db` aside
(the copy is the rollback), pull, start; the file migrates on open.

**Anyone with an Open Actions page open across the deploy should reload
it.** The page's requests changed (the names part in place of the full
summary; the Failing mode's parameters). An old page against the new server
still loads, with no footer line; once a mark exists its Failing mode would
also drop the flaking tests somebody is assigned to, which the new page
keeps.

Feeders: nothing to stop or deploy. Expect replay resends in feeder logs for
the hour around the restart; count nothing as missing until a run has
pushed since.

## Roll back

**Old code does not run against a v12 database.** SQLite refuses a newer
schema version at open; MariaDB refuses a mismatch in either direction.
Either restore the dump (G.2), or:

```
sudo systemctl stop testboard
mysql ... -e "DROP TABLE test_flaky_marks, flaky_mark_history; UPDATE schema_version SET version = 11;"
cd /opt/testboard && git checkout <previous commit>
sudo systemctl start testboard
```

(use the migrate credential; the `UPDATE` is the statement the tool itself
writes, with the version lowered; runbook G.6 names the same two tables.) Both
are clean **only until the first mark is written after the restart**: marks
and their history exist only in the upgraded database, and dropping the two
tables takes every mark with them. The comments the marks posted stay, as
ordinary comments. SQLite: restore the copy taken before the start.
