## What changed, fixes first

**Fixes**

0. **Keep-alive actually keeps alive now, and a rare lost request under
   load is fixed.** Found because its own guard test flaked on CI: a
   timed-out read permanently poisons a `socket.makefile` reader, so every
   idle connection was being silently closed at the first 0.25 s poll tick
   (the 5 s window was fiction) and a request arriving after that tick
   died — a browser papers over a GET by retrying; a POST (a comment, an
   assignment) failed in front of the user, rarely and unreproducibly.
   The wait is now `select`-based with non-blocking peeks, and a reclaim
   grants one grace tick so an in-flight request is served (with the
   close announced on it) rather than dropped. Full story and numbers:
   the status log's evening 2026-08-04 entry. `YieldPeekTest` pins it;
   the previously-flaky guard is 45-for-45 since.

**The feature**

1. **A new page: Timeline** (in the nav on every page). One environment's
   scripts in running order — one row per run of one script, bars on a shared
   clock, test count, duration, red chip when the run contains failures.
   It exists for the poisoned-static-data hunt: when a test fails because an
   earlier script left shared state dirty, the culprit is above it in this
   list. Rows expand on a click anywhere in the row to list the run's tests
   in start order; each test expands in place to its captured output
   (fetched on demand through the existing single-run endpoint — the list
   queries still never touch outputs); partial runs flagged amber as
   "41 of 45 known tests"; ad-hoc re-run blocks selectable in the run picker
   and labelled "partial". Around that core:
   - **A floating Prev/Next stepper** (fixed to the viewport corner) walks
     every failing TEST in the window, opening each output on arrival.
     Labelled as a shortcut, not the verdict — a script can pass and still
     poison shared data.
   - **"Find test"** searches by name (server-side, over `latest_runs` via
     the existing dashboard search — nothing new to maintain), lands on
     the test's row with its output open, and RE-BASES the stepper there —
     Prev/Next continue from the landing, including from a green test
     (Next = first failure after it).
   - **"View in timeline"** deep-links to that exact run's night
     (`timeline.html?environment&script&test&at`), same landing behaviour.
     It appears everywhere a run's output opens: the triage review panels,
     each history row on the test detail page, and the test page's
     standalone run-output viewer. A history row's link carries THAT
     run's time; a run older than the default fortnight widens the
     lookback automatically. The picker's "Earlier runs…" option does the
     same by hand — the cap is 365 days, i.e. retention, so any recorded
     run's night is reachable. The long view still reads only
     `activity_hours`/`script_hours` (~100k tiny rows for a year), never
     `runs`.
   - **Optional vi-ish hotkeys** (`/`, `n`, `p`/`N`, `g`/`G`, `?`, and
     Ctrl-j/Ctrl-k cycling search completions — browsers reserve Ctrl-n),
     all mouse-equivalent, none active while typing in a field except the
     completion pair.

2. **Under it: `script_hours`, the fourth derived table** (migration 7).
   Counts per environment × UTC hour × script × result, carrying the exact
   first-start/last-end per bucket, maintained inside the import transaction
   like the other three, held byte-equal to its `GROUP BY` over `runs` by
   `ScriptHoursTest`. Nothing reads a window of `runs` at request time.

3. **Two new read endpoints**: `GET /api/timeline` and
   `GET /api/scripts/{env}/{script}/runs?from&to`. Nothing existing changed
   shape; `/api/import` is untouched.

## Upgrade procedure

Same drill as the last drop: **a migration runs, so the database copy is the
rollback.**

```bash
# 1. On your machine: confirm what you are shipping.
git log --oneline origin/master..wp-18-timeline
python -m unittest discover          # expect 1328 OK (skipped=1)

# 2. Push (after acceptance).
git push origin wp-18-timeline:master

# 3. On the server, with the feeder NOT importing:
cd /path/to/testboard
sudo systemctl stop testboard

cp testboard.db      testboard.db.pre-2026-08-04          # THE rollback
cp testboard.db-wal  testboard.db-wal.pre-2026-08-04      # if present
cp testboard.db-shm  testboard.db-shm.pre-2026-08-04      # if present

git pull
sudo systemctl start testboard       # first start runs migration 7 — see above
```

**The restart is not optional**, as ever: a stale process serves this drop's
`timeline.html` against handlers that have never heard of `/api/timeline`,
and the page fails with a 404 that looks exactly like a UI bug.

### Check it came up

```bash
grep "script_hours: rebuilt" <server log>                      # migration ran
curl -s "localhost:8000/api/summary?parts=headline" | head -c 200  # 200, JSON
curl -s "localhost:8000/api/timeline?environment=<ENV>" | head -c 200  # 200, JSON
```

In a browser, hard-refresh (Ctrl-Shift-R) and check:

- "Timeline" appears in the nav of every page; the page loads with the
  newest run selected and rows in time order.
- Expanding a row lists its tests; test names link to their detail pages.
- Pick an older run in the picker; the rows change; the URL updates.
- The other pages look exactly as they did — this drop should be invisible
  outside the new tab.

### Rolling back

```bash
sudo systemctl stop testboard
git checkout <previous-commit>
cp testboard.db.pre-2026-08-04 testboard.db           # REQUIRED, not optional:
cp testboard.db-wal.pre-2026-08-04 testboard.db-wal   # v6 code REFUSES a v7 file
sudo systemctl start testboard
```

Anything imported between upgrade and rollback is in the file you just put
aside, not the one you restored — re-run the feeder for the gap (safe: the
server upserts).
