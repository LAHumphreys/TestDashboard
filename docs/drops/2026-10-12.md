## What changed

**Fixed — WP-41: `tools/drop_environment.py` works against MariaDB.**

Production has served MariaDB alone since 2026-10-01, and the tool for
removing a mis-filed environment still accepted only `--db PATH`, a SQLite
file. The storage methods behind the delete already ran on both backends;
the gap was confined to the command line. It now takes the same flags as
`run_server.py` and `drop_stream.py`:

1. `--db PATH` for SQLite, **or** `--db-config CNF` plus `--site-notes PATH`
   for MariaDB. Mutually exclusive; exactly one is required.
2. **`--db` no longer defaults to `testboard.db`.** A forgotten flag used to
   make whatever file sat in the working directory the silent target of an
   irreversible delete. It now refuses.
3. On MariaDB the SQLite-only output is replaced, not printed about nothing:
   no file-size lines, no freed-pages hint, and `--vacuum` says nothing was
   compacted. The "Database:" line shows the option file, never the password.

Only the tool and its tests changed. Run `--dry-run` first, as always.

**New — WP-42: a "Copy output" button on every run-output view.**

Three of the four places the board shows output truncate the inline text to
its last 20 KB, so selecting it by hand never gave the whole output. The
button copies the **full** output the viewer fetched, never the visible
text. It is in the Review panel (Home, compare and the other triage rows),
the Timeline's run rows, and the test page's "Run output" section and its
history rows. It is disabled until the output has loaded (and stays disabled
after a failed fetch or for a run that captured nothing); clicking it reads
"Copied" or "Copy failed" for two seconds. In the Review panel it is the
fourth item in the head row. `static/` only: no request, query or render
pass is added; nothing on first paint. The helper uses the browser clipboard
API (production is served over HTTPS); a hidden-textarea fallback exists for
plain HTTP.

## Deploy

Production (MariaDB). No schema step, so none of the upgrade-tool steps from
earlier notes apply.

```
sudo systemctl stop testboard
cd /opt/testboard && git fetch && git checkout <this drop's commit>
sudo systemctl start testboard
```

**Why restart at all.** Static files are read per request, so WP-42 is live
as soon as the files are on disk. The restart is kept because the standing
rule is "restart after any Python change" and the standard deploy is
pull-then-restart. The only Python that changed is an ops tool, so the
restart is harmless; it keeps the running process equal to the checkout.

Feeders: nothing to stop or deploy.
