## What changed

**Fixed — WP-39: an empty build no longer lingers in the Build picker.**

The production finding, 2026-09-30: after the dodgy environment was
deleted, the build that had only ever run on it stayed in the Build
box as an empty entry. `tools/drop_environment.py` removed the
environment's rows from every table keyed by environment, and `streams`
is not one of them; WP-34's per-build delete settled the build's row,
the environment tool never had. Three things now:

1. **`delete_environment` settles every build it touched**, exactly as
   WP-34's delete does: the row goes if nothing is left of the build,
   else its first/last-seen clock is re-derived from what remains.
   The tool's dry run reports a `streams` line counting the builds
   that would go. Mainline is never settled and never removed.
2. **The server sweeps empty builds once at start-up**, before it
   serves: any build with no `latest_runs` partition is removed and
   named on stdout. This is what removes the one production has now.
   The cost is one seek per row of `streams` (dozens of rows), every
   start, whether or not there is anything to do.
3. A build whose every test is retired is **not** empty: retirement
   keeps the `latest_runs` row. It is kept.

Comments and assignments made from a removed build keep their rows and
lose their origin tag, as with every other stream removal (explicit
UPDATE, identical on both backends).

Nothing in the import path changed. Nothing on any page changed except
that the picker no longer has the empty entry to list.

## Deploy

```
sudo systemctl stop testboard        # or however the service is stopped there
cd /opt/testboard && git fetch && git checkout <this drop's commit>
sudo systemctl start testboard
```

**Restart the server — not optional.** Python changed. The sweep runs in
`run_server.py` between opening the database and building the server, so
a process that is not restarted has not run it and the empty build stays.
No database step. No feeder step. Staging (SQLite) and production
(MariaDB) take the identical procedure.

## Check it came up

1. The server's start-up output, immediately after the database line and
   before `metrics:`, has **`empty builds: removed 1 (build:<name>)`** —
   naming the build that was orphaned on 2026-09-30. Every later start
   says `empty builds: none`.
2. Open any page with the Build box: the empty build is not offered.
3. Everything else as the 2026-09-30 note's checklist.

If the sweep fails, the server does not start: `Cannot tidy the streams
table:` on stderr, exit code 2. On MariaDB that would mean the
application account cannot `DELETE` from `streams` or `UPDATE` the
comment/assignment tables — it already does both for WP-34's delete, so
this is not expected.

## Roll back

```
cd /opt/testboard && git checkout <previous commit>
sudo systemctl start testboard
```

Nothing to restore. The removed row had no results behind it; the
previous build simply lists it again.
