## What changed

**Fixed — WP-39: an empty build no longer lingers in the Build picker.**

The production finding, 2026-09-30: after the dodgy environment was
deleted, the build that had only ever run on it stayed in the Build box as
an empty entry. `tools/drop_environment.py` removed the environment's rows
from every table keyed by environment, and `streams` is not one of them.
Three things now:

1. **`delete_environment` settles every build it touched**, as WP-34's
   per-build delete does: the row goes if nothing is left of the build,
   else its first/last-seen clock is re-derived. The tool's dry run reports
   a `streams` line counting the builds that would go. Mainline is never
   settled and never removed.
2. **The server sweeps empty builds once at start-up**, before it serves:
   any build with no `latest_runs` partition is removed and named on
   stdout. This removes the one production has now. Cost: one seek per row
   of `streams` (dozens), every start.
3. A build whose every test is retired is **not** empty (retirement keeps
   the `latest_runs` row). It is kept.

Comments and assignments made from a removed build keep their rows and lose
their origin tag, as with every other stream removal.

**New — WP-40: acknowledged failures.** A person looking at a failing test
can acknowledge it, with a reason, for **1 to 7 days**. While it is live
the test stops counting as failing and is shown beside the failing figure
("12 failing · 65 acknowledged"), never subtracted silently. In operator
terms:

- **Two tables.** `test_acknowledgments` is the CURRENT acknowledgment per
  (stream, environment, script, test); `acknowledgment_history` is one row
  per act (acknowledge, extend, clear). Both are small and human-rate and
  both are removed with their environment or build (the environment tool
  and the build delete know about them). Expired rows stay until cleared.
- **One stream at a time.** An acknowledgment of mainline's failure does
  not reach a build, and the other way round.
- **Owned.** Acknowledging assigns the test, in the same transaction;
  **unassigning drops the acknowledgment** (history row, reason
  "unassigned"). Assignment is per test and acknowledgment per stream, so
  unassigning a test drops every stream's acknowledgment of it.
- **Decays.** No indefinite acknowledgment anywhere; the API and storage
  both refuse anything outside 1–7 whole days. Open Actions has an
  **Expiring** list (a day or less left, or already expired and still
  failing) with Extend.
- **A pass inside the window does not end it.** A test that is failing now
  and has a live acknowledgment is acknowledged, whatever happened between.
- **Not `known_failure_reason`.** That is what a feeder declares
  (`FAILED_AS_EXPECTED`); this is what a person does. Untouched.
- **Endpoints:** `POST /api/acknowledgments/bulk`, `POST
  /api/acknowledgments/clear`, `GET /api/acknowledgments` (README). Every
  place that shows a failing count (Home, Watch, product cards, a build's
  tiles) also carries `acknowledged`.
- **Cost.** Nothing on the push path. The headline's one-pass rollup is
  unchanged; with no live acknowledgment on a stream the new read costs
  zero statements. The performance A/B against `master` is measured
  separately and appended to `UPGRADE_PLAN_STATUS.md`; no number is quoted
  here until it is.

## Deploy

**STAGING (SQLite).** The app migrates the file on first open; a v11 file
cannot go back to v10 code, so the copy is the rollback. Adjust paths.

```
sudo systemctl stop testboard
cp /var/lib/testboard/testboard.db /var/lib/testboard/testboard.db.pre-wp40-$(date +%Y%m%dT%H%M%S)
cd /opt/testboard && git fetch && git checkout <this drop's commit>
sudo systemctl start testboard
```

Migration 11 has no Python step, so it prints no progress line — it is two
`CREATE TABLE`s and is over before the server listens. Read the start-up
output (below) and open the Metrics page, which names the schema version.
Copy `-wal`/`-shm` files too if the service leaves any beside the `.db`
after a stop (it normally checkpoints them away).

**PRODUCTION (MariaDB), per `docs/MARIADB_MIGRATION.md` §G.** The schema
moves only by the tool; the app never runs DDL and refuses a version
mismatch in both directions. Order matters:

```
# 1. G.1 -- root recreates the migrate account (fresh password) and the
#    operator rewrites ~/.testboard-migrate.cnf. Delete both again at the end.
# 2. G.2 -- the dump IS the rollback. Check it is not tiny.
mysqldump --defaults-file=~/.testboard-migrate.cnf \
    --single-transaction --routines --triggers testboard \
    > testboard-preupgrade-$(date +%Y%m%dT%H%M%S).sql
ls -l testboard-preupgrade-*.sql

# 3. Get the new code onto disk but do NOT restart yet (the tool is in it):
cd /opt/testboard && git fetch && git checkout <this drop's commit>

# 4. Dry run. It runs nothing. READ the SERVER line:
python3 tools/upgrade_mariadb_schema.py upgrade \
    --config ~/.testboard-migrate.cnf --dry-run
```

Expected: `SERVER: may keep running` (the step only creates), with one step,
10 to 11, and two `CREATE TABLE` statements. **If it says `SERVER: STOP IT
FIRST`, do what it says** (`sudo systemctl stop testboard`) — that would
mean the ledger changed after this note was written.

```
# 5. Upgrade (the server may still be running). It verifies by itself:
python3 tools/upgrade_mariadb_schema.py upgrade \
    --config ~/.testboard-migrate.cnf
#    Every table must report "matches the v11 oracle". Any mismatch: do NOT
#    start the new code; restore from the dump (G.2).

# 6. Now the restart -- NOT optional: Python changed, and the old process
#    would refuse the new schema at its next start anyway.
sudo systemctl stop testboard        # if still running
sudo systemctl start testboard

# 7. Delete the migrate account and ~/.testboard-migrate.cnf.
```

Feeders: nothing to stop or deploy. Expect replay resends in feeder logs
for the hour around the restart; count nothing as missing until a run has
pushed since.

## Check it came up

1. Start-up output has **`empty builds: removed 1 (build:<name>)`** after
   the database line and before `metrics:` — the build orphaned on
   2026-09-30. Later starts say `empty builds: none`. (There is no
   start-up line for the schema version.)
2. **Metrics** page: schema version **11**.
3. Home: the failing tile has an **Acknowledged** figure beside it and
   there is an **Acknowledged** queue next to Still failing (empty at
   first). The Build box does not offer the empty build.
4. Acknowledge ONE failing test you can spare (selection bar, or the test
   page): reason, 1–7 days, an assignee. The Failing tile drops by one,
   Acknowledged rises by one, and the test is in the queue with its
   expiry; Watch shows the same on its card.
5. **Open Actions** has the **Expiring acknowledgments** list. A fresh
   7-day acknowledgment will not be in it; one set to 1 day will, with
   Extend. Clear the test you acknowledged; the counts go back.
6. Everything else as the 2026-09-30 note's checklist (Metrics "Waited,
   mean" near zero; the build page and its Difference tab).

If the server will not start with a schema message, the upgrade did not
run (or the code is on the wrong side of it): that is the refusal doing its
job; do not edit `schema_version` by hand to get past it.

## Roll back

**Staging (SQLite)** — before anyone has acknowledged anything or after,
the file is refused by the old code, so restore the copy:

```
sudo systemctl stop testboard
cp /var/lib/testboard/testboard.db.pre-wp40-<stamp> /var/lib/testboard/testboard.db
cd /opt/testboard && git checkout <previous commit>
sudo systemctl start testboard
```

Anything written since the copy (comments, assignments, imports the feeder
has not re-pushed) is lost with it.

**Production (MariaDB)** — either restore the dump (G.2), or, if only the
two new tables exist and nobody has relied on them:

```
sudo systemctl stop testboard
mysql ... -e "DROP TABLE test_acknowledgments, acknowledgment_history; UPDATE schema_version SET version = 10;"
cd /opt/testboard && git checkout <previous commit>
sudo systemctl start testboard
```

(use the migrate credential; the `UPDATE` is the statement the tool itself
writes, with the version lowered.) Both are clean **only until the first
acknowledgment is written after the restart**: the acknowledgments, and the
assignments they made, exist only in the upgraded database. Rolling back
the WP-39 half alone needs nothing: the sweep's one delete was of a row with
nothing behind it.

- **The migrate-credential path on production** was exercised only as far
  as the runbook describes it; there is no rehearsal against a copy of
  production's data.
- **The pass-then-fail-inside-the-window rule** (still acknowledged) is as
  decided and has not been seen by a tester; expect the question.
- **Performance on production's data or engine.** The A/B against `master`
  is separate (see `UPGRADE_PLAN_STATUS.md`); dev-scale SQLite, not
  production.
- **Known edges, deliberately not changed** (log, 2026-10-01 WP-40 built):
  an acknowledgment on a currently-passing test sits dormant and goes live
  if it fails again; the Assigned and Acknowledged tabs overlap;
  unassigning from mainline drops a build's acknowledgment of the same
  test; expired rows and history are never pruned; an extended
  acknowledgment keeps its original timestamp and shows the extender.
- **WP-39's sweep on production's MariaDB**: plain `SELECT … NOT EXISTS`,
  `DELETE … WHERE id = ? AND NOT EXISTS` and the tag-clearing UPDATEs, run
  on 12.3 only. **How the production orphan came to be** is inferred from
  the code (`delete_environment` never touched `streams`); if the start-up
  line names a different build, say so — that is a different story.
