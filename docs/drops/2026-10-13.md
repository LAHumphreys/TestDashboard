## What changed

**New — WP-43: the three home-dashboard charts show which failures are
nobody's yet.**

Failing by environment, most failures by script and failing runs per day each
split the red into **Unassigned**, **Assigned** (a new blue) and **Muted**
(the existing grey), with a legend on each card. A developer glancing at the
board sees how much of the red is nobody's without a hover. Bar order, end
labels and click targets are unchanged. The per-day chart carries a caption:
its split is as things stand now, so a past day's columns recolour as tests
are taken. Its data table gains Unassigned, Assigned and Muted columns.

For the operator, the API:

1. `/api/summary?parts=headline` carries two new fields: `assigned` on each
   `by_environment` entry and on each `top_failing_scripts` entry.
2. A new part, `/api/summary?parts=assigned_trend`, returns the per-night
   split (`FAIL_ASSIGNED`, `FAIL_MUTED`) with the same parameters and
   validation as the headline. The home page requests it in the same
   parallel batch as the headline, so the page makes four data requests
   where it made three; nothing new is awaited before first paint.
3. **The full, unsliced payload's shape is unchanged.** It deliberately does
   not carry the split (Open Actions fetches it on first paint).

An older server answers the new part with a 400; the page then draws the
previous two-series card, so a page and a server a version apart degrade
instead of breaking. No schema change: the figures are computed from the
tables already there, memoized per environment and dropped by the same
writes (a push, an assignment, a mute) that drop the existing figures.

**Tooling — a 90-night performance seed** (`tools/dev/perf/`), development
only; not part of the served build.

## What was NOT verified

- **No real browser has rendered any of this**, as with every drop here. The
  UI was walked with a DOM shim and urllib reads against a play server only.
  How the new blue and the three-segment bars look, and how the legend sits
  in a narrow card, is unseen.
- **MariaDB was measured on a local 12.3**; production's 10.3 is exercised
  only by CI. The query plan was read by hand on the newer server and is
  indicative.
- **The trend part's cost at 90 days with many assignments is the owner's
  open decision; nothing for the operator to do.** On the 90-night seed
  (SQLite, cold, in-process), the part costs about 23 ms at the default 14
  days and 101 ms at 90 days with 65 assignments (the reference estate's
  figure), memoized until the next push or assignment change. At 1,000
  assignments it costs about 317 ms and 1,553 ms; on local MariaDB the
  statement alone is 2.2 to 3.0 s at 90 days with 1,000 assignments. The
  card paints late and nothing else waits; the headline and full payload are
  unchanged within noise. The owner chooses between accepting this as built,
  a covering index (a migration, a package of its own) and a cap.
