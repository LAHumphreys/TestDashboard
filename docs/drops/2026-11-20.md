## What changed

**New — mark a test as flaky.** A developer marks a test with a reason and a
cadence of 2 to 10: it counts as failing only once its last N runs have
failed. While it fails fewer times in a row than that it is **flaking**:
taken off the failing figures and out of New failures and Still failing,
listed in a **Flaking** tab in Triage, shown as FLAKING in its own colour (a
mauve), and named beside the figure it was taken out of ("+4 flaking"). It
still counts against the pass rate. The night it fails past its cadence it is
a new failure again, red, reading FLAKING → FAIL. A mark covers mainline and
every build of the test's environment.

- **Marking**: the selection bar (a Flaky group after Mute: Mark as flaky,
  Set cadence, Unmark), the Review panel, and the header of the test's own
  page. The reason is posted as a comment on the test; "Flaky mark history"
  on the test's page lists every act.
- **Home**: the failing figures name what is set aside; "All clear" gains
  "Set aside: N muted · N flaking"; the three charts draw flaking as its own
  part after muted; the Flaking tab is a triage queue like its neighbours
  (Output, Review and the acts on every row, a Streak cell reading "2 in a
  row, failing after 3") and is drawn only where something is flaking.
  There is no Flaking tile.
- **All tests**: a FLAKING filter beside FAIL once a test in view is flaky;
  FAIL then leaves the flaking tests out, and the two together are every
  failing test.
- **Open Actions**: unassigned flaking tests are left out until they fail
  past their cadence, and a line under the count says so; an assigned one
  stays, reading FLAKING. Its Failing mode leaves them out too.

The computed signal that was worded "flaky — flips about 1 run in 3" now
reads "flips about 1 run in 3", so that on screen "flaky" always means a
mark or a default somebody set.

**New — a default flaky cadence for an environment.** For an environment
where one failure is usually not the test. Set on Admin, in the
environment's row, with a cadence of 2 to 10 and a required reason: every
test there with no mark of its own is then judged as a marked test is, on
every surface, the per-day chart included. It reads a test's most recent
runs, not one night's: one failure on each of two nights counts. A test's
own mark wins over the default. A row under a default reads FLAKING with no
"flaky" pill; its Review panel says the cadence is the environment's default
and offers "Mark as flaky" and "Change the default", which opens the
environment's row on Admin. Change and Remove take a reason too, and every
act is kept under the row's History. **Setting, changing or removing a
default re-judges the whole environment at once, for everybody**: New
failures, Still failing, Newly fixed, the Flaking tab and every night of the
chart move with it.

**New page — Admin**, in the navigation bar after Metrics. It holds
Environments (the expected test counts, products, and the Flaky default
column) and People. **Both sections have left the foot of Open Actions**;
anyone who looks for "Manage people" or "Environment expectations" there
finds them on Admin.

**Changed for everyone — "Failing runs per day" draws once, a moment after
the rest of the page.** Home's first batch is three data requests where it
was four: the chart's split (`parts=assigned_trend`) is asked for once the
headline has drawn. A first load shows "Loading…" in the chart's place and
then draws it once, split. A Reload or a change of scope keeps the previous
chart, dimmed, until the new one lands. If the part fails or takes more
than ten seconds the chart draws its totals with an amber line under it,
"Not split: … Reload to try again." Nothing else on the page waits for it.

**Changed — a muted test that has stopped running leaves Not run.** A test
under a live mute whose latest run is older than the Not run cutoff is left
out of the Not run tile, tab and badge and of All tests' "Not run recently"
filter. The tile names how many ("+5 muted"). It is still in the Muted tab
and is back in Not run the moment its mute expires. No schema change.

For the operator, the API (the README has the shapes):

1. `POST /api/flaky/bulk`, `POST /api/flaky/unmark`: the mark's acts.
2. `PUT /api/environments/{environment}/flaky-default` with
   `{"username", "cadence", "reason"}`: sets or changes a default (cadence 2
   to 10) or removes it (`"cadence": null`). A body with no `cadence` key is
   a 400; the reason is required for all three and is at most 500
   characters; an unknown environment is a 404.
3. `GET /api/environments`: each environment gains `flaky_default` (null, or
   `{cadence, set_by, set_at, reason}`) and `flaky_default_history` (newest
   first: `{id, action, cadence, reason, actor, acted_at}`).
4. `GET /api/summary?parts=queue&queue=flaking`: the Flaking tab's rows.
   `GET /api/summary?parts=names`: the catalogue alone, which Open Actions
   now asks for in place of the full summary.
5. `flaky` on browse, queue and Open Actions rows and on test detail, with
   `flaky.source` (`"mark"` or `"default"`); `flaking` counts on the summary
   and on Watch's cards; `status.flaky_defaults`, the environments in scope
   that have a default.
6. `result=FLAKING` on `GET /api/dashboard`, and `result=FAIL` narrowed to
   the FAIL rows that are not flaking; `FAIL_FLAKING` on every night of
   `parts=assigned_trend`.
7. `tools/drop_environment.py` deletes an environment's marks, its default
   and the history of each with the rest of it; its dry run counts them
   (the `environment_flaky_defaults` and `flaky_default_history` lines).

**What it costs, and where.** With no mark and no default anywhere, every
read runs the statements it ran before, on both backends, and the push path
is the same either way. Where they exist, measured cold, in-process and
alternated on generated data at production's scale (SQLite ; a local
MariaDB 12.3):

| | SQLite | MariaDB 12.3 |
|---|---|---|
| Home's headline, 50 marks ; 1,000 marks | +6.2 ms on 28.6 ; +11.4 | +17.0 ms on 93.0 ; +35.8 |
| Home's headline, a default of 2, 50 failing tests in the environment ; 500 | +2.8 ; +11.8 to +12.7 | +5.8 ; +17.3 to +18.1 |
| the same at a default of 3 or more, 500 failing | +30.2 | +45.8 |
| The per-day chart's late part, 14 days, a default of 2, 50 failing a night ; 500 | +36 to +37 ; +135 to +139 | +71 to +75 ; +583 to +600 |
| The same on a build's tab | +22 to +27 | +39 to +69 |

The chart's part is off first paint and kept until the next push or act; its
cost grows with the failed runs in the window, not with the environment's
tests. A default of 3 or more costs more than 2 because it reads each
failing test's recent runs (the list reads +15 to +44 ms at 500 failing),
and it keeps what it read until the environment's next push. Open Actions
as a page is faster than before the drop on SQLite and level on MariaDB.

**Tooling** — fixtures and a page mode in the performance harness
(`tools/dev/perf/`), development only; not part of the served build.

## Deploy

Production (MariaDB). The schema moves only by the tool; the app never runs
DDL and refuses a version mismatch in both directions. Order matters.

```
# 1. Credentials per runbook G.1 (the migrate account; delete it at the end).
# 2. G.2 -- the dump IS the rollback. Check it is not tiny.
mysqldump --defaults-file=~/.testboard-migrate.cnf \
    --single-transaction --routines --triggers testboard \
    > testboard-preupgrade-$(date +%Y%m%dT%H%M%S).sql
ls -l testboard-preupgrade-*.sql

# 3. Get the new code onto disk but do NOT restart yet (the tool is in it):
cd /opt/testboard && git fetch && git checkout <this drop's commit>

# 4. Dry run. It runs nothing. READ the SERVER line:
python3 tools/upgrade_mariadb_schema.py upgrade \
    --config ~/.testboard-migrate.cnf --dry-run
```

**From step 3 until the restart in step 6 the old process serves the new
pages**: static files are read per request. In that window Open Actions
lists its rows under an error banner with its filters unfilled (the old
server answers 400 to the names request the new page makes), and Admin
shows no Flaky default column. Do steps 3 to 6 in one sitting, a minute or
two; or stop the server before step 3 if you would rather have it down than
half-new. Feeders defer either way.

Four `CREATE TABLE`, two `CREATE INDEX`, no `ALTER TABLE`. The tool also

`Verifying against a fresh v13 schema...` and one line per table, twenty of
them, each of the form `ok    schema:runs            matches the v13 oracle`,

do: restart the server, ...`. **Any line that reads `DIFFERS from the v13
oracle`: do NOT start the new code; restore from the dump (G.2).** Run a
second time it says `STOP: already at schema version 13. Nothing to

   reads "Set aside: N muted" where muted failures exist, and "Failing runs

5. Mark ONE failing test you can spare (tick its row; the selection bar's
   Flaky group: a cadence, a reason, Mark as flaky). If it has failed fewer
   times in a row than the cadence its row reads FLAKING, the failing figure
   drops by one and names "+1 flaking", and the Flaking tab appears with the

   the test has one new comment with your reason. (If it has already failed
   as many times in a row as the cadence it stays where it was with a
   "flaky" tag: that is the mark working.) Unmark it: the counts go back,
   and the tab goes once nothing is flaking.

   choose "2 in a row", give a reason, Save. The cell then reads "2 in a

   its caption ends "by today's environment default". Remove it, with a

## Roll back

**Old code does not run against a v13 database.** SQLite refuses a newer
schema version at open; MariaDB refuses a mismatch in either direction.
Either restore the dump (G.2), or:

```
sudo systemctl stop testboard
mysql ... -e "DROP TABLE flaky_default_history, environment_flaky_defaults, flaky_mark_history, test_flaky_marks; UPDATE schema_version SET version = 11;"
cd /opt/testboard && git checkout <previous commit>
sudo systemctl start testboard
```

(use the migrate credential; the `UPDATE` is the statement the tool itself
writes, with the version lowered; runbook G.6 names the same four tables.
The previous commit is the drop of 2026-10-13.) Both are clean **only until
the first mark or default is written after the restart**: they and their
history exist only in the upgraded database, and dropping the tables takes
every one with them. The comments the marks posted stay, as ordinary
comments. After the statement above the tool's dry run reads 11 again and
offers the same two steps. SQLite: restore the copy taken before the start.

## What was NOT verified

- **No real browser has rendered any of this**, as with every drop here: the
  marks, the Admin page, the default's editor and its History, the chart
  drawing once. It was walked with a DOM shim and read over HTTP on seeded
  copies, where the Flaking tab's total, the FLAKING filter's total, the
  headline's figures and every night of the chart agreed with the runs. How
  the mauve reads against the red and the grey, the Admin table at narrow
  widths, where focus lands when an editor opens and whether the amber "Not
  split" line is noticed are unseen: the first look after deploy is the
  check.
- **The upgrade's output above was run on a local MariaDB 12.3**, against
  an empty database put at 11 by removing the four tables from a fresh
  schema; the rollback statement was run there too. On production's 10.3
  stream CI builds a database through every step of the tool and runs the
  whole suite on it, green on the merged code.
- **MariaDB was measured on a local 12.3**; production's 10.3 is exercised
  only by CI. **No query plan has been read on 10.3 for the default's two
  new statements**: the per-day chart's read for an environment with a
  default, and Open Actions' rows read by keys where a default is in
  scope. CI asserts their results there, not their plans; their plans were
  read on the 12.3. The Flaking tab's rows do have a plan guard that CI
  runs on 10.3. The Not run reads with a live mute have none on MariaDB.
- **At a default of 3 or more, a test's recent runs are held until the
  environment's next push**, where other answers are held a minute. A push
  through the server drops them; another process deleting runs does not.
  After a tool that deletes runs, or any direct edit, restart the server,
  as `tools/drop_environment.py` already says when it finishes.
- **Two people marking the same unmarked test at the same instant on
  MariaDB**: one gets a 500 and the mark is made once. The default's `PUT`
  re-reads under a lock and does not have the gap. Known and left.
- **Decided in the build and still the owner's to confirm; nothing for the
  operator to do.** Unmarking a test under a default can make that night's
  run a New failure, because it is then judged by the default alone. On an
  environment that runs each test more than once a night, the Flaking
  figures count tests as they stand now and the chart counts the failed
  runs tolerated that night, so the two numbers differ and both are right.
  The selection bar's Unmark stays enabled over rows that are flaking by a
  default and have no mark to remove.
- **Costs the owner has accepted or left open**: the headline where marks
  exist is over the bar its design set (the first row of the table above),
  accepted for now; the per-day chart's part with many marks or many
  assignments at 90 days reads about a second on SQLite and more on
  MariaDB, off first paint, undecided. One reading stays unexplained: Home
  as a page on the local MariaDB with no marks read 9% slower in one order
  and faster with the sides swapped, statement for statement equal.
- Nothing was measured on production's data; every figure is on generated
  development data at production's scale. The code needs SQLite 3.15 or
  newer, which matters only to a SQLite deployment and is stated nowhere
  else.
