## What changed, fixes first

**Fixes**

1. **Retiring a test now sticks.** It could not before, and this was live in
   production: the site feeder re-pushes its whole recent window every 10
   minutes, and ANY re-import of a test — including a byte-identical re-send
   of an old run — cleared its retirement and posted an "Automatically
   un-retired" comment. Every retirement was silently undone within 10
   minutes. Now an unchanged record is recognised (see 3) and skipped
   entirely; only a genuinely new or changed run un-retires.
   **Cleanup:** tests un-retired by the bug are still un-retired. Find them by
   their "Automatically un-retired" comments and re-retire by hand; they will
   stay retired now.

2. **`/api/summary` was 6 s mean on production — the dominant term is gone.**
   Your perf report was right: `activity_buckets` (3.5 s mean, 70% of the
   summary) was answered by SQLite with a **full scan of the runs UNIQUE
   index** — all 4.4M rows, on every summary, Time page, stale filter and
   environments call, growing every night. Migration 6 adds `activity_hours`
   (runs per environment × hour × result, maintained inside the import
   transaction, backfilled once) and both window queries read it instead.
   Measured on the dev copy: that query 607 ms → **2.3 ms**; `/api/summary`
   751 ms → **172–206 ms**; `/api/time` 630 ms → **40 ms**.

**Changes testers will see**

3. **The home page paints in stages.** Three requests instead of one: the
   headline (tiles, charts, every tab's count — 14 KB instead of 97 KB) paints
   first, the open tab's rows follow, other tabs fetch on first click with a
   "Loading queue…" line. Full-payload `/api/summary` still works unchanged
   for anything else that calls it; a contract test pins the parts to the
   whole.

**Invisible, but the reason the mount gets quieter**

4. **A byte-identical re-import writes nothing.** Before: every 10-minute
   push rewrote up to 10,000 `runs` rows AND re-REPLACEd their compressed
   outputs — measured **~2.3 KB of WAL per unchanged record, ~23 MB per
   push, ~3.3 GB/day** of pointless writes through the network mount, evicting
   the page caches every reader depends on and invalidating the trend memo ~20
   times per push. Now: **0 bytes written, ~11× faster to answer** (0.46 s →
   0.04 s per 2,000 records, dev copy). `runs.output_fingerprint` (SHA-1 of
   the output text) is how "identical" is decided without reading blobs back.
   **The first push after the upgrade still writes everything once** — it is
   stamping fingerprints on rows that predate the column. From the second push
   on, an all-unchanged cycle is read-only.
   The import response now carries `unchanged`; **`updated` still includes
   unchanged records on the wire**, so the deployed feeder's logs and sums are
   unaffected. No feeder change is needed or shipped.

## Upgrade procedure

The difference from the last drop: **a migration runs, so the database copy is
the rollback**, not a nicety.

```bash
# 1. On your machine: confirm what you are shipping.
git log --oneline origin/master..wp-17-summary-perf
python -m unittest discover          # expect 1288 OK (skipped=1)

# 2. Push (after acceptance).
git push origin wp-17-summary-perf:master

# 3. On the server, with the feeder NOT importing:
cd /path/to/testboard
sudo systemctl stop testboard

cp testboard.db      testboard.db.pre-2026-07-31          # THE rollback
cp testboard.db-wal  testboard.db-wal.pre-2026-07-31      # if present
cp testboard.db-shm  testboard.db-shm.pre-2026-07-31      # if present

git pull
sudo systemctl start testboard       # first start runs migration 6 — see above
```

**The restart is not optional**, as ever: a stale process serves this drop's
HTML against the previous drop's handlers, and this drop changed both.

### Check it came up

```bash
grep "activity_hours: rebuilt" <server log>                 # migration ran
curl -s "localhost:8000/api/summary?parts=headline" | head -c 200   # 200, JSON
curl -s "localhost:8000/api/summary" | head -c 200                  # 200, JSON (old shape)
```

In a browser, hard-refresh (Ctrl-Shift-R) and check:

- Dashboard tiles and charts appear promptly; the open queue's rows follow.
- Clicking another triage tab shows "Loading queue…" then rows; clicking back
  is instant.
- Retire a test (or use one the bug un-retired), wait through two feeder
  pushes (~20 min), confirm it is STILL retired.
- After the first post-upgrade feeder push completes, the second one should be
  quick — in the perf log, `upsert_runs` collapses.

### Rolling back

```bash
sudo systemctl stop testboard
git checkout <previous-commit>
cp testboard.db.pre-2026-07-31 testboard.db      # REQUIRED, not optional:
cp testboard.db-wal.pre-2026-07-31 testboard.db-wal   # v5 code REFUSES a v6 file
sudo systemctl start testboard
```

Anything imported between upgrade and rollback is in the file you just put
aside, not the one you restored — re-run the feeder for the gap (safe: the
server upserts).
