## What changed

**New — Refresh and Follow on the Timeline page.** Results now arrive while
a run is still going, and a full run can take seven hours. The Timeline
showed the run as it was when the page loaded; catching up meant a full
reload that lost every open row and the scroll position.

- **Refresh** (button beside the Run picker) re-reads the selected run in
  place. If the server's answer is identical to what is drawn, nothing is
  redrawn. If it differs, the page re-renders, re-opens the rows the reader
  had open (each re-fetches its tests), and keeps the scroll position. The
  status line beside it reads "Updated HH:MM UTC" and, once a refresh finds
  something new, "new results at HH:MM UTC".
- **Follow** (toggle) does the same on a timer: one check every ten
  seconds, each scheduled after the previous one completes (never an interval, so a slow
  server cannot stack requests), only while the tab is visible (a hidden
  tab skips the fetch and catches up the moment it is shown). A failed
  check goes to the status line and the next check still happens; it never
  raises the error banner. Follow applies to the newest run only — an
  earlier run is finished by construction — and switches off, with the
  button disabled, when an earlier run is selected. Turning it on refreshes
  immediately. `follow=1` travels in the page URL so a link can carry it.

Files: `static/timeline.js`, `static/timeline.html`, `static/style.css`,
`static/whatsnew.html`, `tests/test_frontend_calls.py`
(`TimelineLiveRefreshTest`, +8, all failing against the previous page).

**Why it is front-end only.** The server's newest block already grows as
hours fill in: `analytics.complete_passes` trims blocks only at the OLD
edge of the lookback window, never the new one, so an in-progress run IS
the newest block and a re-fetch of "newest block" returns its new rows.
No endpoint changed.

**Load, stated — measured, dev-scale copy (production is ~4× the data).**
One poll is 27 ms mean / 42 ms p95 over HTTP on the heaviest environment;
of that, ~8 ms is the bare round trip (a trivial endpoint costs the same),
6–12 ms is `known_environments()` validating the name (a scan of the
`latest_runs` primary key — a one-line follow-up, see below), ~8 ms is
parsing and grouping ~800 hour buckets, ~3 ms is the 68 KB JSON, and the
two derived-table reads are under 1 ms. Hammered by ten concurrent
clients it sustained 238 requests/s (p95 71 ms). At one poll every ten
seconds, ten followers are one request a second — under half a percent
of that. **The cadence was 60 s in the first draft and dropped to 10 s on
the user's call after these numbers**; the constant is `FOLLOW_POLL_MS`
in `static/timeline.js` and everything worded from it follows.

**Follow-up, not in this drop (Python):** `_handle_timeline` validates
the environment with `known_environments()` — a full key scan — where
`Storage.environment_exists()` (three index seeks) answers the same
question; its own docstring says so. Worth a minute in the next
server-side drop; it is the largest single cost of a poll after the
transport itself.

## What was NOT verified

- **No real browser has rendered this**, as with every drop here. The live
  evidence is a DOM-shim driver (`.scratch/net/wp32_drive_timeline.mjs`,
  not in the repo) against a server booted from this commit on a seeded
  copy of the dev estate, 43 checks passing: an unchanged Refresh leaves
  the same DOM node; a run imported into the newest block appears on
  Refresh with the open row re-opened and its detail re-fetched; Follow on
  refreshes at once and chains exactly one poll; the poll draws the next
  run; a hidden tab makes no fetch and re-schedules; an earlier run
  switches Follow off and disables it; a `follow=1` link opens following.
  The poll was invoked by hand (the ten-second timer captured), so **the
  real cadence has never been observed ticking** — only that each tick is
  scheduled after the previous one completes.
- **Scroll restoration** is `window.scrollTo(0, scrollY)` after the
  re-render; the shim has no viewport, so this is unexercised. A page
  that jumps to the top on refresh would be this line.
- **The failure stepper's position** ("3 of 12 failing tests") is rebuilt
  on a changed refresh and starts over; the test-search box keeps its
  text. Deliberate: the row set changed underneath it. Worth a look if a
  tester notices.
- **A run that pauses for more than six hours** becomes two blocks; Follow
  then follows the newer one. That is the existing block rule, not this
  drop, but a follower would see the earlier half "disappear" into the
  previous run entry of the picker.
